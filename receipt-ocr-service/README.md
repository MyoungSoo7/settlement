# receipt-ocr-service

법인카드 **영수증 필드 추출(비전 OCR)** 의 자체 구현과, 그것을 판정하는 **도메인 채점 하네스**.

`card-service` 의 영수증 대사는 지금 외부 LLM(Gemini) 호출에 얹혀 있다
(`ExtractReceiptFieldsPort` ← `GeminiReceiptOcrAdapter`). 포트 주석이 스스로 밝히듯 그 자리는
"AI 비전 OCR 구현 교체 지점" 이다. 이 서비스는 그 자리에 꽂을 자체 구현을 만들고, **바꿔도 되는지를
숫자로 판정**하는 것을 목표로 한다.

> **현재 상태: Phase 0 완료** — 합성 골든셋 + 채점 하네스 + Gemini baseline 실측까지.
> 로컬 모델 서빙(Phase 1)과 파인튜닝(Phase 2)은 아직 없다.

---

## 왜 정확도로 채점하지 않는가

필드 정확도(총액 일치율)로 채점하면 운영에서 의미 없는 숫자가 나온다. 실제로 갈리는 건
`ExpenseReceiptMatcher` 가 내리는 **최종 대사 판정**이고, 그 판정마다 사람이 치르는 비용이 다르다.

그래서 이 하네스는 모델 출력을 **운영과 같은 대사 규칙**에 통과시킨 뒤 판정끼리 대조한다
(`src/receipt_ocr/domain/matcher.py` 는 Java 매처의 이식본이고, 정책은 `tests/test_matcher.py` 가
케이스로 못박는다).

**오답 비용은 비대칭이다.**

| 오답 종류 | 무슨 일이 벌어지나 | 가중치 |
|---|---|---|
| `NEEDS_REVIEW` 로 보냄 | 사람이 리뷰 큐에서 확인 — 설계된 안전 경로 | 1 |
| 추출 실패(503) | 재시도·수기 처리 | 3 |
| 리뷰 대상을 기계가 조기 종결 | 사람이 봤어야 할 걸 멋대로 닫음 | 10 |
| `MATCHED` → `MISMATCHED` 오종결 | **멀쩡한 영수증이 종결됨** — 재첨부 외엔 못 되돌림 | 25 |
| `MISMATCHED` → `MATCHED` 통과 | **증빙 없는 지출이 승인됨** | 25 |

정확도 한 줄이 아니라 **치명 오류 두 칸**이 합격 판정의 실질 기준이다.

## 사용법

```bash
python -m venv .venv && .venv/Scripts/python.exe -m pip install -r requirements-dev.txt

# 1) 합성 골든셋 + 이미지 생성 (시드 고정 — 같은 시드는 같은 셋)
.venv/Scripts/python.exe -m receipt_ocr build --count 35

# 2) baseline 측정 (GEMINI_API_KEY 는 환경변수 또는 저장소 루트 .env 에서 읽는다)
.venv/Scripts/python.exe -m receipt_ocr run --save

# 3) 테스트 + 뮤테이션 점검
.venv/Scripts/python.exe -m pytest tests/ -q
.venv/Scripts/python.exe tools/mutation_check.py
```

`PYTHONPATH=src` 가 필요할 수 있다(패키지를 설치하지 않고 돌릴 때).

### 지연 수치의 전제

`--workers 1`(기본)일 때만 p50/p95 가 모델 응답시간이다. 병렬을 켜면 큐잉이 섞여 하네스 처리량을
재게 된다.

## 골든셋

시나리오 5종 × 촬영조건 7종을 **교차**해서 만든다.

| 시나리오 | 정답 판정 |
|---|---|
| `CLEAN` 영수증 = 매입 | `MATCHED` |
| `NEXT_DAY` 심야 결제로 전표가 +1일 | `MATCHED` (±1일 허용이 흡수) |
| `NO_DATE` 거래일 미인쇄 | `NEEDS_REVIEW` |
| `AMOUNT_TAMPERED` 금액이 매입과 다름 | `MISMATCHED` |
| `STALE_DATE` 과거 영수증 재첨부 | `MISMATCHED` |

촬영조건: `PRISTINE` / `FADED`(감열지 퇴색) / `CRUMPLED`(구김) / `SKEWED`(기울임) /
`LOW_LIGHT`(저조도) / `LOW_RES`(멀리서 촬영) / `GLARE`(반사광 밴드).

3건에 1건은 **할인·포인트 사용**이 붙어 소계·할인·공급가액·부가세·합계가 함께 찍힌다 — 금액
후보가 여러 개일 때 합계를 고르는지 보는 축이다.

> **합성의 한계**: 여기서 나온 점수는 실물 영수증 성능이 아니다. 렌더러의 글자는 완벽한 디지털
> 글리프라서 실제 감열지의 번짐·인쇄 불량을 흉내만 낸다. **모델 간 상대 비교와 하네스 검증**에만
> 쓰고 절대 성능 주장에는 쓰지 않는다. 한국 카드 영수증 공개 라벨셋이 사실상 없어서(공개 영수증
> 데이터셋은 대개 해외 영수증 기반) 실물 셋 확보는 별도 과제다.

## Baseline 실측 (2026-08-21)

`gemini-2.5-flash`, 35건, 순차 호출, 임계 0.80 — 운영 어댑터와 **문자 단위로 같은 프롬프트**
(`tests/test_gemini_provider.py` 가 Java 원문과 대조해 드리프트를 막는다).

| 지표 | 값 |
|---|---|
| 대사 판정 일치율 | **88.6%** |
| 치명 — 멀쩡한 영수증 오종결 | **1건** |
| 치명 — 증빙 없는 지출 통과 | 0건 |
| 총액 정확 일치 | **100%** |
| 거래일 허용내 일치 | 93.8% |
| 리뷰 큐 유입률 | 17.1% |
| 추출 실패율 | 8.6% (전부 **벤더측 503**) |
| ECE (신뢰도 교정) | 0.026 |
| 지연 p50 / p95 | **5.3s / 7.2s** |

### 핵심 발견 — 신뢰도가 스칼라 하나라서 생기는 오종결

반사광에 덮인 거래일시를 Gemini 는 `2020-08-11` 로 읽고 **신뢰도 0.98** 을 붙였다(정답
`2026-03-11`). 총액은 정확히 읽었다.

```
정답 : 총액 30810 | 거래일 2026-03-11 | 매입 30810 @ 2026-03-10 23:52 KST
예측 : 총액 30810 | 거래일 2020-08-11 | confidence 0.98
판정 : MISMATCHED — "거래일 불일치: 영수증 2020-08-11 vs 매입일(KST) 2026-03-10"
```

신뢰도가 **추출 전체에 대한 값 하나**라서 쉬운 필드(총액)의 확신이 어려운 필드(거래일)의
불확실성을 덮었다. 그 결과 6년 틀린 날짜가 0.80 게이트를 통과해 **종결 상태**로 갔고, 멀쩡한
영수증이 재첨부 없이는 못 돌아온다.

→ 자체 구현이 노릴 자리는 여기다: **필드별 신뢰도**. 총액은 확신하되 날짜는 모른다고 말할 수
있으면, 이 케이스는 종결이 아니라 리뷰로 흐른다(비용 25 → 1).

### 그래서 목표는 "이기는 것"이 아니다

총액 정확 일치가 이미 100% 라 정확도로 baseline 을 이길 여지는 크지 않다. 자체 구현의 논거는
정확도가 아니라 다음 셋이다.

1. **필드별 신뢰도** — 위 오종결을 구조적으로 없앤다.
2. **지연** — p50 5.3초는 업로드 화면에서 체감되는 시간이다.
3. **외부 전송 제거** — 영수증에는 상호·금액·카드번호 일부가 찍힌다. 벤더측 503 이 8.6% 였다는
   것도 같은 이야기의 다른 면이다(가용성이 남의 손에 있다).

Phase 2 의 합격 기준은 따라서 **"총액 정확도를 100% 로 유지한 채, 치명 오류 0 · 지연 대폭 단축"**
이다. 정확도 우위가 아니다.

## 구조

```
src/receipt_ocr/
├── domain/         # ExtractedReceipt VO + 대사 규칙 (Java 이식본, 채점 기준)
├── synth/          # 합성 영수증 생성기 + Pillow 렌더러
├── eval/           # 골든셋 영속 · 채점기 · 러너 · CLI
└── providers/      # 추출 프로바이더 (base 계약 + Gemini baseline)
tools/mutation_check.py   # 정책을 하나씩 망가뜨려 테스트 탐지력을 증명
```

### 테스트

129개. 그리고 통과만으로는 검증력의 증거가 되지 않으므로, `tools/mutation_check.py` 가
**정책 문장 9개를 하나씩 뒤집어** 테스트가 잡아내는지 확인한다(현재 9/9 검출).

실제로 이 점검이 공백을 하나 찾아냈다 — ECE 테스트가 구간 크기를 2:2 로 잡아 **가중 평균 여부를
구분하지 못하고** 있었다.

### 알려진 제약

- **폰트**: 한글 폰트가 없으면 렌더가 두부(□)로 나와 골든셋이 통째로 무의미해진다. 그래서
  `resolve_font_path()` 는 못 찾으면 예외로 끊는다. 도커 이미지에는 나눔고딕/Noto CJK 설치 필요.
- **tzdata**: 매입일 KST 환산이 대사 정책이라 tz DB 를 런타임 의존성으로 고정했다(시스템 tz DB 가
  없는 플랫폼에서 `ZoneInfoNotFoundError` 로 죽는다).
- **비용 표시**: 토큰 단가를 `--price-in/--price-out` 으로 주지 않으면 비용은 0 으로 나온다.
  모르는 가격을 지어내지 않는다.
- 리포트에 토큰 사용량이 아직 집계되지 않는다(프로바이더는 수집하고 있으나 `Prediction` 이
  들고 오지 않음).
