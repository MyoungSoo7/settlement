## 1. 배경과 문제

셀러(CEO)에게는 **확정된 정산금**이 쌓인다. 그 돈은 정산일까지 놀고 있고, 셀러는 그것을 굴리고 싶어 한다.
그런데 플랫폼이 투자를 붙이면 세 가지가 동시에 문제가 된다.

| 문제              | 구체적 손상                                                                     |
| ----------------- | ------------------------------------------------------------------------------- |
| **판단 근거 부재** | "이 종목이 살 만한가"를 감으로 답하면 플랫폼이 책임질 수 없다                  |
| **재원 초과 집행** | 정산금보다 많이 집행하면 플랫폼이 손실을 떠안는다                              |
| **사후 검증 불가** | 집행 후 점수가 바뀌면 "그때 왜 샀나"를 설명할 수 없다                          |

investment-service 는 **재무 기반 점수로 판단 근거를 만들고, 확정 정산금 안에서만 집행**한다. 핵심 설계
판단은 하나다 — **판단 근거를 집행 시점에 박제한다.**

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 투자 판단에 재현 가능한 근거를 붙인다 | 3축 점수·등급이 결정적 함수로 산출 |
| G2 | 재원을 넘는 집행이 불가능하다 | `available = 확정정산금 − 집행합`, 초과 시 거부 |
| G3 | 사후에 판단 근거를 되짚을 수 있다 | 신청 시점 점수·등급을 주문에 영구 보존 |
| G4 | 남의 재원을 건드릴 수 없다 | 셀러 식별자를 JWT 주체에서 파생 + 소유권 대조 |
| G5 | 중복 제출이 이중 집행이 되지 않는다 | Idempotency-Key 로 선점, 중복 409 |

### 2.2 비목표

| # | 비목표 | 이유 |
|---|---|---|
| N1 | 실제 증권 체결 | 모의 집행 — 증권사 연동은 범위 밖 |
| N2 | 시세 기반 지표(PER/PBR) 생성 | 시세는 market, 재무는 financial 소관. 조인만 한다 |
| N3 | 투자 권유·수익 보장 | 점수는 근거이지 권유가 아니다 |
| N4 | 재원의 원천 관리 | 확정 정산금은 settlement 소관 — 여기는 프로젝션으로 읽는다 |

## 4. 제품 범위 — 기능 맵

| 영역 | 기능 |
|---|---|
| 투자점수 | 3축(수익성 35·안정성 35·성장성 30) 0~100 산출 |
| 등급 | AAA~CCC 7등급, 투자적격 경계 60(BBB) |
| 주문 | 신청 → 승인 → 집행 / 거절·취소 |
| 재원 | 확정 정산금 프로젝션 − 집행 합 |
| 스냅샷 | 신청 시점 점수·등급 영구 보존 |
| 멱등 | Idempotency-Key 선택 헤더 |

## 5. 핵심 유스케이스

### UC-1. 셀러가 종목의 투자점수를 본다

1. 재무제표(financial-statements)를 입력으로 3축 점수를 계산한다.
   - **수익성 35** = 영업이익률 20 + ROA 15
   - **안정성 35** = 부채비율 20(낮을수록 좋음) + 자기자본비율 15
   - **성장성 30** = 매출 YoY 15 + 순이익 YoY 15
2. 총점으로 등급을 매긴다 — ≥90 AAA / ≥80 AA / ≥70 A / ≥60 BBB / ≥50 BB / ≥40 B / 그 미만 CCC.
3. **60점(BBB) 이상이 투자적격**이다.

> 결측은 0점(보수적)으로 환산한다. 직전 연도가 통째로 없으면 성장성만 중립(50%)으로 준다 —
> "모른다"를 "나쁘다"로 단정하지 않되, 유리하게도 해석하지 않는다.

### UC-2. 집행이 재원을 넘지 않는다

1. 셀러가 주문을 신청한다(`REQUESTED`).
2. 승인 후 집행 시 **① 소유권을 먼저 검증**하고(403), **② `FOR UPDATE` 로 재원을 재검증**한다.
3. 재원이 부족하면 주문을 `REJECTED` 로 **확정 커밋**한다 — 거절 사실이 롤백으로 사라지지 않게
   `noRollbackFor` 를 건다.
4. 집행 성공 시 `investment.executed` 를 Outbox 로 발행한다.

### UC-3. 판단 근거가 박제된다

1. 신청 시점의 점수·등급이 주문에 `scoreAtOrder`/`gradeAtOrder` 로 저장된다.
2. 이후 재무가 갱신돼 점수가 바뀌어도 **그 주문의 근거는 변하지 않는다.**
3. 사후 감사에서 "그 시점에 무엇을 보고 샀나"를 답할 수 있다.

### UC-4. 중복 제출이 이중 집행이 되지 않는다

1. 클라이언트가 `Idempotency-Key` 를 실어 보낸다.
2. `INSERT ... ON CONFLICT DO NOTHING` 으로 키를 선점한다.
3. 이미 있는 키면 **409** 를 반환한다 — 다만 **원 응답 재생(replay)은 지원하지 않는다**(명시적 한계).

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 점수는 3축 가중 합(35/35/30)으로 0~100 이다 | `InvestmentScorePolicy` |
| FR-2 | 부채비율은 낮을수록 높은 점수를 준다 | 동상(AT_MOST 밴드) |
| FR-3 | 결측·미매칭은 0점으로 환산한다 | 동상 |
| FR-4 | 직전 연도 전체 부재 시 성장성은 중립 50% | 동상 |
| FR-5 | 재무제표가 아예 없으면 예외로 거부한다 | `InvestmentInvariantViolationException` |
| FR-6 | 등급 경계는 90/80/70/60/50/40 이다 | `InvestmentGrade` |
| FR-7 | 투자적격 임계는 60 이다 | `INVESTABLE_THRESHOLD` |
| FR-8 | 집행 가능액 = 확정정산금 합 − EXECUTED 집행 합 | 단일 판정 지점 `covers()` |
| FR-9 | 집행은 소유권 검증 → 재원 재검증(FOR UPDATE) 순이다 | 집행 서비스 |
| FR-10 | 재원 부족 거절은 확정 커밋된다 | `noRollbackFor` |
| FR-11 | 신청 시점 점수·등급을 보존한다 | 주문 컬럼 + DB CHECK |
| FR-12 | 셀러 식별자는 JWT 주체에서 파생한다 | `AuthPrincipal.userId()` |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **점수는 결정적 함수** — 같은 입력이면 같은 점수. 구간 기반이라 경계를 테스트로 고정할 수 있다 | `InvestmentScorePolicy` |
| BR-2 | **모름은 0점** — 보수적으로 환산한다. 다만 성장성의 전기 부재만 중립 처리 | 동상 |
| BR-3 | **재원 공식은 하나** — 이 공식 밖의 재원 산정을 금지한다 | `covers()` 단일 지점 |
| BR-4 | **소유권 먼저, 재원 나중** — 남의 주문인지부터 막고 재원을 본다(정보 노출 최소화) | 집행 경로 순서 |
| BR-5 | **근거 박제** — 집행 이후 점수 변동이 과거 판단을 바꾸지 않는다 | 스냅샷 컬럼 |
| BR-6 | **발행은 Outbox 경유** | `investment.executed` |

## 12. 역산에서 드러난 격차

### G-1. 재원 프로젝션이 조용히 멈출 수 있다

`app.kafka.enabled` 기본값이 `false` 다. 운영에서 주입이 빠지면 `settlement.confirmed` 소비가 **조용히
중단**되고 `seller_funding_view` 가 갱신되지 않는다. 그러면 셀러의 집행 가능액이 실제보다 **적게** 보인다 —
안전한 방향이지만, 원인 없이 "왜 투자가 안 되지"가 된다.

### G-2. 커버리지 게이트가 비대칭이다

부모 빌드의 **핵심 도메인 INSTRUCTION 80% 엄격 목록에 `investment.domain.*` 이 없다.** 금융 도메인인데
상위 게이트에서 빠져 있고 LINE 90% 만 적용된다.

### G-3. 멱등이 응답 재생을 지원하지 않는다

중복 키는 409 로 거부된다. **원 응답을 다시 돌려주지 않으므로**, 네트워크 단절로 응답을 못 받은
클라이언트는 결과를 알 수 없다 — 조회로 확인해야 한다. 명시적 한계지만 API 계약에 드러나야 한다.

### G-4. 추천 유니버스가 코드·마이그레이션에 박혀 있다

추천 종목 세트가 하드코딩(코스피 대형주)이고, 특정 시점 추천 데이터가 마이그레이션에 INSERT 로
박제돼 있다. 유니버스를 바꾸려면 배포가 필요하다.

### G-5. 레거시 시간 경로가 남아 있다

일부 오버로드가 `LocalDateTime.now()` 를 시스템 존으로 직접 호출한다(신규 경로는 `Clock` 주입).
테스트 호환을 위한 잔존이지만, 그 경로로 만들어진 주문은 시간 기준이 다르다.

### G-6. 점수의 입력 품질이 관측되지 않는다

결측을 0점으로 환산하는데(BR-2), **몇 개 항목이 결측이었는지가 점수와 함께 남지 않는다.** 60점이
"고르게 낮아서"인지 "절반이 결측이라서"인지 사후에 구분할 수 없다.
