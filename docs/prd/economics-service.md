## 1. 배경과 문제

기업 신용평가와 투자 판단은 **개별 기업의 숫자만으로는 완성되지 않는다.** 같은 부채비율이라도 기준금리가
1%일 때와 4%일 때의 의미가 다르다. 그런데 거시 지표를 쓰려면 매번 한국은행 ECOS API 를 붙여야 했다.

| 문제              | 구체적 손상                                                                    |
| ----------------- | ------------------------------------------------------------------------------ |
| **맥락 결손**     | 기업 재무를 시점의 거시 환경과 함께 읽을 수 없다                              |
| **지표 추가 비용** | 새 지표를 볼 때마다 코드·스키마를 고쳐야 하면 "일단 넣어보자"가 불가능해진다  |
| **주기 불일치**   | 일별 지표와 월별 지표를 같은 시계열로 다루면 월 중 어느 날짜에 꽂을지가 매번 임의 판단이 된다 |

economics-service 는 ECOS 지표를 한 곳에서 수집·보관하고 공개 조회로 서빙한다. 핵심 설계 판단은 하나다 —
**지표 카탈로그를 코드가 아니라 데이터로 둔다.**

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 지표 추가가 배포 없이 가능하다 | 카탈로그 row 추가만으로 새 지표가 수집·조회된다 |
| G2 | 주기가 다른 지표를 한 시계열 규칙으로 다룬다 | 월별 지표는 항상 해당 월 1일에 한 점 |
| G3 | 변동 계산을 소비측이 반복 구현하지 않게 한다 | 변동액·변동률을 조회 시 제공 |
| G4 | 계산 불가를 값으로 위장하지 않는다 | 직전값 0 이면 변동률은 `null` |

### 2.2 비목표 (의도적으로 하지 않는 것)

| # | 비목표 | 이유 |
|---|---|---|
| N1 | 파생값 저장 | 저장하면 원본과 파생이 어긋날 수 있다. 계산은 읽기 시점에 한다 |
| N2 | 지표 예측·전망 | 별도 서비스(forecast, Python)의 책임 |
| N3 | 다중 공급자 추상화 | 현재 공급자는 ECOS 하나 |
| N4 | 지표 정의의 코드화(enum) | 카탈로그를 데이터로 두는 것이 G1 의 전제다 |

| 영역 | 기능 |

## 5. 핵심 유스케이스

### UC-1. 새 지표를 코드 변경 없이 추가한다

1. 운영자가 `indicators` 에 row 를 추가한다(코드·이름·단위·주기 D/M + ECOS 통계·항목 코드).
2. 다음 수집 실행이 그 지표를 자동으로 포함한다.
3. 조회 API 가 별도 배포 없이 새 지표를 서빙한다.

> ECOS 통계 코드가 틀렸다면 **row 만 고치면 된다.** 실제로 `BASE_RATE` 는 설계 스펙상 월별이었으나
> ECOS 722Y001 이 일별이라 카탈로그에서 D 로 정정했다.

### UC-2. 소비측이 변동률을 받아 쓴다

1. 소비측이 시계열 조회로 관측치를 받는다.
2. 응답에 직전 대비 변동액과 변동률(소수 4자리 HALF_UP)이 포함된다.
3. 직전값이 0 이면 변동률은 `null` 이다 — 소비측은 이를 **"변동 없음"이 아니라 "계산 불가"** 로 읽어야 한다.

### UC-3. 월별 지표가 시계열에 한 점으로 꽂힌다

1. ECOS 응답의 월별(M) 시각을 파싱한다.
2. 해당 월 **1일**로 정규화해 저장한다.
3. 월 내 어느 날 발표됐든 시계열에서는 한 점이며, `(지표, 관측일)` 유일성이 성립한다.

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 지표 정의는 DB row 로 관리한다 | `indicators` 테이블 |
| FR-2 | 주기는 D/M 뿐이다 | `chk_indicator_cycle` |
| FR-3 | 월별 관측일은 해당 월 1일로 정규화한다 | ECOS 응답 파싱 단계 |
| FR-4 | `(지표, 관측일)` 은 유일하다 | `uq_iv_indicator_date` |
| FR-5 | `indicatorCode`·`observedDate`·`value`·`source` 는 필수다 | 생성 시점 검증 |
| FR-6 | 변동값은 저장하지 않고 조회 시 계산한다 | `IndicatorValue.changeFrom` |
| FR-7 | 서로 다른 지표끼리 변동 계산을 시도하면 거부한다 | 동상 — 이종 지표 가드 |
| FR-8 | 직전값이 0 이면 변동률은 `null` 이다 | 동상 — 0 나눗셈 방어 |
| FR-9 | 조회는 인증 없이, 수집은 내부 키로만 | `AdminApiKeyFilter` |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **카탈로그가 정의의 단일 출처** — 지표 추가·정정은 데이터 변경이지 코드 변경이 아니다 | `indicators` + `Indicator` 레코드 |
| BR-2 | **월별은 1일** — 주기가 다른 지표를 한 규칙으로 다루기 위한 정규화. 임의 판단을 없앤다 | 수집 파싱 |
| BR-3 | **파생은 읽기 시점 계산** — 저장하지 않으므로 원본과 어긋날 수 없다 | `changeFrom` |
| BR-4 | **계산 불가는 null** — 0 이나 무한대로 위장하지 않는다. 변동액은 그대로 제공한다 | 동상 |
| BR-5 | **재수집은 대체** — 같은 (지표, 관측일)의 새 값이 기존 값을 덮는다 | UPSERT |

## 12. 역산에서 드러난 격차

> 이 절은 "고쳐야 할 목록"이 아니라 **현재 상태의 정직한 기록**이다.

### G-1. 형제 위성과 어휘가 갈라져 있다

`ValueSource` 가 여기서는 `SEED`/`ECOS` 다. 형제 서비스 market 은 **같은 문제를 인지하고**
`SAMPLE`/`EXCHANGE` 로 재정의하면서 근거를 남겼다 — *"SEED 는 적재 수단이고 KRX 는 공급자 이름이다.
공급자가 바뀌면 도메인 상수가 거짓이 된다."* 그 논리는 economics 에도 그대로 적용되지만 반영되지 않았다.
결과적으로 **소비측이 두 위성의 서로 다른 어휘를 외워야 한다.**

### G-2. 카탈로그가 데이터인 것의 이면

지표 추가가 쉬운 대신, **카탈로그 값의 출처와 정정 이력을 추적할 구조가 없다.** `BASE_RATE` 를 M→D 로
정정한 근거는 마이그레이션 주석에만 있다. 누가·왜 그 값을 그렇게 정했는지는 다음 사람이 알 수 없다.

### G-3. `null` 변동률의 의미가 계약에 없다

BR-4 는 "계산 불가"를 `null` 로 표현한다. 그런데 그 의미가 API 응답 계약(스키마·문서)에 명시됐는지는
역산 범위에서 확인하지 않았다. 소비측이 `null` 을 0 으로 읽으면 "변동 없음"으로 오독한다.

### G-4. 도메인 예외가 generic 이다

필수값·이종지표 검증이 `IllegalArgumentException` 이다. market 과 같은 비대칭이며, 도메인 위반이
인프라 예외와 타입으로 구분되지 않는다.

### G-5. 수집 실패의 관측 경로가 얕다

수집 실패는 상태 조회로 드러나지만, 이 서비스는 **메트릭·알람 배선이 없다**(Kafka·Prometheus 잡 없음).
지표가 며칠째 갱신되지 않아도 소비측이 먼저 알아차리는 구조다.
