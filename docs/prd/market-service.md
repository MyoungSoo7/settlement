## 1. 배경과 문제

플랫폼 안에는 이미 **기업의 재무제표**(financial-statements)와 **뉴스 평판**(company)이 있다. 그런데 투자
판단·기업 신용평가에서 가장 자주 필요한 축인 **시장 가격**이 없었다. 그 공백이 세 가지 문제를 만든다.

| 문제               | 구체적 손상                                                                        |
| ------------------ | ---------------------------------------------------------------------------------- |
| **판단 근거 결손** | 재무는 아는데 시가총액을 몰라 "비싸게 거래되는가"를 말할 수 없다                   |
| **중복 수집**      | 시세가 필요한 서비스마다 각자 외부 API 를 붙이면 키·쿼터·정규화 규칙이 N벌로 흩어진다 |
| **신뢰도 혼동**    | 샘플 데이터와 거래소 실시세가 섞이면 소비측이 "이 값을 믿고 계산해도 되는가"를 알 수 없다 |

market-service 는 KRX 일별 시세를 한 곳에서 수집·보관하고 공개 조회로 서빙한다. 핵심 설계 판단은 하나다 —
**계산하지 않고 사실만 제공한다.**

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 종목별 일별 시세·시총을 단일 출처로 제공 | 같은 (종목, 거래일) 이 항상 한 행 |
| G2 | 값의 신뢰도를 소비측이 구분할 수 있게 표기 | 모든 관측치가 `SAMPLE`/`EXCHANGE` 중 하나를 갖는다 |
| G3 | 수집 실패가 조용히 지나가지 않게 한다 | 실패 시 상태 조회로 드러나고 다음 실행이 재수집한다 |
| G4 | 인증 없이 조회 가능, 수집은 통제 | GET 공개 / `/admin` 은 내부 키 필요 |

### 2.2 비목표 (의도적으로 하지 않는 것)

| # | 비목표 | 이유 |
|---|---|---|
| N1 | **PER·PBR 등 밸류에이션 계산** | 재무 데이터 소유권이 흐려진다. 조인은 소비측 몫이며 `guard.mjs` 가 기계로 차단한다 |
| N2 | 실시간 틱 스트리밍 | 별도 서비스(market-stream, Go)의 책임 |

| N4 | 다중 공급자 추상화 | 현재 공급자는 KRX 하나. 도메인은 공급자 이름을 모른다(신뢰도만 안다) |

| 영역 | 기능 |
|---|---|

## 5. 핵심 유스케이스

### UC-1. 소비측이 시가총액으로 밸류에이션을 계산한다

1. 소비측이 `GET /api/market/stocks/{code}/latest` 로 최신 시세를 받는다.
2. 응답에 `marketCap`(BigInteger)·`closePrice`(BigDecimal)·`source` 가 포함된다.
3. 소비측은 `source == EXCHANGE` 인지 확인하고, 자기 재무 데이터와 조인해 PER/PBR 을 **자기 책임으로** 계산한다.

> 이 서비스가 계산해 주지 않는 것이 계약이다. 계산해 주면 "어느 시점 재무와 조인했는가"라는 책임이
> 시세 서비스로 넘어온다.

### UC-2. 일별 수집이 돌고 재수집이 값을 대체한다

1. 07:30 KST 스케줄러가 최근 `lookback-days`(기본 7)를 대상으로 KRX 수집을 실행한다.
2. 각 관측치는 `(종목, 거래일)` UNIQUE 로 UPSERT 된다 — 늦게 정정된 공시가 기존 행을 대체한다.
3. 같은 날 여러 번 돌아도 행이 늘지 않는다.

### UC-3. 운영자가 특정 구간을 재수집한다

1. 운영자가 `X-Internal-Api-Key` 를 실어 `POST /admin/market/sync` 를 호출한다.
2. 키가 틀리면 필터에서 거부된다(gateway 에 라우팅돼 있지 않아 외부에서 직접 닿지 않는다).
3. `GET /admin/market/sync/status` 로 결과를 확인한다.

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 종가·시가·고가·저가·전일대비·등락률은 `BigDecimal` 로 다룬다 | `StockQuote` 레코드 타입 |
| FR-2 | 거래량·상장주식수·거래대금·시가총액은 `BigInteger` 로 다룬다 | 동상 — 원 단위 총액의 정밀도 보존 |
| FR-3 | 받은 값을 파생 계산 없이 그대로 보존한다 | `StockQuote` 주석·구현 |
| FR-4 | `stockCode`·`baseDate`·`closePrice`·`source` 는 필수다 | 생성 시점 검증 |
| FR-5 | `(종목, 거래일)` 은 유일하다 | `uq_sq_stock_date` |
| FR-6 | 종가는 `> 0`, 나머지 가격·수량은 `>= 0` 이어야 한다 | DB CHECK 3종 |
| FR-7 | 전일대비·등락률은 음수를 허용한다 | CHECK 대상에서 제외(하락이 정상) |
| FR-8 | 시장 구분은 KOSPI/KOSDAQ/KONEX 뿐이다 | `chk_stock_market` |
| FR-9 | 조회는 인증 없이, 수집은 내부 키로만 | `SecurityConfig` + `AdminApiKeyFilter` |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **밸류에이션 금지** — PER/PBR/priceEarnings/priceToBook 대입 코드는 유입 자체가 차단된다 | `guard.mjs` `MARKET-NO-VALUATION`(실시간·pre-commit·CI 3중) |
| BR-2 | **신뢰도는 도메인 언어로** — `SAMPLE`(근사, 신뢰 불가) / `EXCHANGE`(거래소 공시). 적재 수단(`SEED`)이나 공급자 이름(`KRX`)은 도메인 상수가 아니다 | `ValueSource` + 재정의 마이그레이션 |
| BR-3 | **종목 마스터는 피드가 정한다** — 그날 피드에 등장한 종목을 upsert. 별도 등록 절차 없음 | `Stock` |
| BR-4 | **재수집은 대체다** — 같은 (종목, 거래일)의 새 값이 기존 값을 덮는다. 이력을 쌓지 않는다 | `uq_sq_stock_date` UPSERT |

## 12. 역산에서 드러난 격차

> 이 절은 "고쳐야 할 목록"이 아니라 **현재 상태의 정직한 기록**이다. 판단 근거를 남기는 것이 목적이다.

### G-1. 값 무결성 CHECK 가 기존 행을 검증하지 않는다

값 CHECK 3종이 `NOT VALID` 로 추가됐다. 신규 행만 검증되고 **기존 행은 검증되지 않은 채 남는다**.
VALIDATE 단계가 별도로 수행됐는지는 역산 범위에서 확인하지 않았다. 즉 "종가는 항상 양수다"는
**신규 데이터에 대해서만** 참이다.

### G-2. 관리 키가 미설정이면 개발 통과다

`AdminApiKeyFilter` 는 키가 설정되지 않았을 때 통과시킨다. 운영에서 `app.security.internal-key-required=true`
주입이 빠지면 수집 트리거가 무인증으로 열린다. 안전장치가 **배포 절차에 의존**한다는 뜻이다.

### G-3. 도메인 예외가 generic 이다

필수값 검증이 `IllegalArgumentException` 이다. `guard.mjs` 의 `OO-DOMAIN-GENERIC-IAE` 는 금융 5서비스에만
적용되므로 위성은 대상 밖이다 — 의도된 비대칭(위성은 `*-rules` 스킬로 커버)이지만, 그 결과 이 서비스의
도메인 위반은 인프라 예외와 타입으로 구분되지 않는다.

### G-4. 값 집합 변경 마이그레이션이 순서 함정을 갖는다

`ValueSource` 재정의는 **파티션드 테이블 + CHECK 제약 해제 → 값 치환 → 재생성** 순서에 의존했다.
순서를 틀리면 CHECK 위반으로 전량 실패한다. 같은 형태의 변경이 또 필요하면 동일한 함정을 밟는다 —
마이그레이션 주석에 근거가 남아 있는 것이 유일한 방어다.

### G-5. 소비측이 신뢰도를 확인하는지 강제할 수단이 없다

`source` 를 제공하지만 소비측이 `SAMPLE` 을 걸러 쓰는지는 이 서비스가 알 수 없다. 계약 테스트가
없으므로(이벤트를 쓰지 않는다) 오용은 런타임에도 드러나지 않는다.
