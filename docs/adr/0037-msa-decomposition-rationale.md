# ADR 0037 — MSA 서비스 경계 근거 (사업 전제 + 분해 기준 6축)

- 상태: Accepted (구조 변경 없음 — 기존 18서비스+gateway 구조에 대한 소급 근거 문서화)
- 일자: 2026-08-18

## 컨텍스트

이 프로젝트는 order-commerce·settlement 를 코어로 loan·investment·account·organization·card·
insurance·deposit·operation·financial-statements·economics·company·market·common-data·ai·board·
education 까지 총 18개 서비스 + gateway(+ 폴리글랏 7종)로 분해되어 있다. 서비스 각각이 왜
분리됐는지에 대한 개별 ADR(0018 chargeback, 0023 company, 0031 seller-tier 등)은 있지만,
**전체 지형에서 "왜 이 개수·이 경계인가"를 설명하는 문서는 없었다.**

리뷰에서 다음 지적이 나왔다: 지금 분해는 도메인 역할(팀이 감당하는 책임 단위)이 아니라 **데이터
원천 단위**로 잘게 쪼개진 것처럼 보인다 — 특히 financial-statements/economics/market/
common-data/company 는 "DART/ECOS/KRX/data.go.kr/뉴스라는 소스가 다르다"는 이유만으로 나뉜
위성 서비스 묶음이다. MSA 는 서비스 운영에 필수 요소가 아니라 선택이고, 도메인 하나가 분리되면
현실 조직에서는 최소 전담 1인 ~ 최대 1개 팀이 필요하다. 근거 없이 잘게 쪼갠 경계는 "다뤄보고 싶은
기술에 도메인을 꿰맞춘 결과"로 읽히며, 이는 정확히 시니어 포트폴리오가 피해야 할 인상이다.

목표는 이 프로젝트가 서 있는 **가정된 사업 컨텍스트를 명시**하고, 거기서 파생되는 **분해 기준
프레임워크**를 세운 뒤, 기존 18개 서비스를 그 기준에 대조해 "왜 분리했는가/왜 분리 근거가
약한가"를 서비스별로 정직하게 서술하는 것이다. **구조 자체는 바꾸지 않는다** — 이미 구현된
이벤트 계약·통합테스트·게이트 자산을 지키면서 근거를 사후(retrofit)로 정리한다.

## 결정

### 1. 가정한 사업 전제 (명시적 선언)

흩어진 도메인들을 하나의 일관된 사업 서사로 묶기 위해 다음을 전제로 고정한다:

- **채널**: 자사 오픈마켓형 이커머스 플랫폼 단독 운영. 네이버 스마트스토어·쿠팡 등 외부 채널
  연동은 가정하지 않는다 — 연동이 생기면 채널 어댑터는 order-service 안에 흡수하는 것이 맞고,
  그 자체로 별도 서비스 분리 사유는 아니다(§3 C그룹 판단 근거와 동일 원리).
- **풀필먼트**: 3PL/자체 물류창고 미보유. 배송은 외부 택배사 위탁이며 order 는 배송 상태
  동기화만 담당한다 — 그래서 이 프로젝트에 WMS/재고창고 도메인이 없다.
- **사업 모델**: 이커머스 본체(B2C) + **셀러 대상 임베디드 파이낸스 사업부 확장**. 즉 커머스
  플랫폼이 입점 셀러를 대상으로 선정산대출·법인카드·보험·투자·예치금 관리를 겸영하는 그룹사
  구조(쿠팡–쿠팡페이, 네이버–네이버파이낸셜류와 동형). 이 전제가 성립해야 loan/card/insurance/
  deposit/investment/account 가 "같은 회사 안의 서로 다른 사업 단위"로 분리될 근거가 생긴다 —
  이 전제 없이는 이들도 그냥 잘게 쪼갠 데이터 묶음일 뿐이다.
- **조직 가정**: 각 사업 단위는 최소 1개 스쿼드가 전담하고, 스쿼드 간 배포·장애·규제 책임이
  분리되어야 한다. 실제 작성자는 1인이지만, 매 분리 결정마다 **"이게 실제 조직이라면 몇 개 팀이
  필요한가"** 를 검증 질문으로 쓴다 — 답이 "굳이 안 나눠도 된다"면 그 분리는 재고 대상이다.

### 2. 분해 기준 프레임워크 (6축)

새 서비스 분리/기존 서비스 존치 판단에 아래 6축을 쓴다. **데이터 원천이 다르다는 이유 하나만으로는
분리 사유가 되지 않는다** — 최소 2축 이상 강하게 걸려야 별도 서비스로 정당화한다.

| 축 | 질문 | 강하게 걸리는 예 |
|---|---|---|
| ① 정합성 경계 | 다른 도메인과 한 트랜잭션에 묶여야 하는가, 최종 일관성으로 풀리는가 | settlement 원장은 order 트랜잭션과 묶이면 안 됨(ADR 0020) |
| ② 규제/라이선스 경계 | 별도 인허가·감사·규제 보고 대상인가 | 보험대리점업(insurance), 여신 리스크(loan/card), 예치금 규제(deposit) |
| ③ 장애 격리 | 이 서비스 장애가 다른 서비스 SLA 를 깨면 안 되는가 | LLM 벤더 장애(ai)가 결제를 막으면 안 됨, 운영신호(operation)가 비즈니스 경로와 얽히면 안 됨 |
| ④ 변경/배포 주기 | 변경 빈도·리스크 등급이 달라 같이 배포하면 위험한가 | 정산 로직(상시 변경) vs 재무제표 조회(분기 배치) |
| ⑤ 팀 인지 부하 | 한 팀이 도메인 지식 전체를 감당 가능한가 | settlement 자체가 이미 578파일로 한 팀의 최대치(§3 A그룹) |
| ⑥ 데이터 오너십 | 이 서비스가 쓰기 권한을 가진 시스템인가, 외부 데이터의 조회 프록시인가 | financial/economics/market/commondata 는 쓰기 권한이 외부 기관(DART/ECOS/KRX/data.go.kr)에 있음 — 오너십 약함 |

### 3. 18개 서비스 분류

**A그룹 — 강한 경계** (2축 이상 강하게 걸림, 분리 근거 명확)

| 서비스 | 근거(해당 축) |
|---|---|
| order-commerce | 커머스 트랜잭션 루트, 나머지 전 서비스의 이벤트 소스 |
| settlement | ①③⑤ — 원장 정합성 + 셀러 정산 SLA + 이미 한 팀 최대 인지부하(578파일, ADR 0020) |
| loan | ②③ — 여신 리스크관리, 대출 부실 전파가 정산/카드로 새면 안 됨 |
| card | ②③ — 카드업 리스크, 승인/매입 실시간 SLA(`master_limit >= Σ sub_limit` 불변식) |
| insurance | ②③⑤ — 완전판매 게이트 등 보험업 고유 규제, 커머스와 완전히 다른 규칙 체계(GA 도메인) |
| deposit | ①② — 예치금은 셀러 자금이라 회사 자산과 원장상 격리해야 하는 규제적 요구(에스크로 성격) |
| account (GL) | ①②⑤ — 회계원장 단일 진실원, 감사 대상, "발행 없는 소비 전용" 자체가 통제 경계 |
| organization | ⑤⑥ — 조직/멤버십 마스터, card 등 여러 금융 서비스가 참조하는 진짜 오너 |
| investment | ②③ — 투자 상품/재원 검증, 손익 리스크가 정산과 분리돼야 함 |

**B그룹 — 중간 경계** (1축이 강하고 나머지는 보조, 존치는 되나 A만큼 필연적이지 않음)

| 서비스 | 근거 |
|---|---|
| operation | ③ — 운영 관제·인시던트가 비즈니스 요청 경로와 절대 얽히면 안 됨(fire-and-forget, 절대 throw 금지) |
| ai | ③④ — LLM 벤더 장애 격리 + 완전히 다른 비용/트래픽 프로파일 |
| board / education | ④⑤ — 콘텐츠성 도메인, 배포 주기·트래픽 패턴이 코어와 다름. 팀 경계 근거는 약함(합쳐도 큰 무리는 없음) |

**C그룹 — 약한 경계** (사실상 데이터 소스 단위 분리, 정직하게 인정)

| 서비스 | 실제 분리 이유 | 왜 팀 경계는 아닌가 |
|---|---|---|
| financial-statements | DART 배치 수집 | ⑥ 조회 전용, 쓰기 오너십이 외부에 있음 |
| economics | ECOS 배치 수집 | 상동 |
| market | KRX 시세 수집/피드 | 상동. 다만 실시간 스트리밍 파생(market-stream, 폴리글랏)이 붙어 있어 ④(배포 주기) 근거는 상대적으로 있음 |
| common-data | data.go.kr 범용 커넥터 | 상동, 사실상 데이터소스 등록형 프레임워크 하나일 뿐 |
| company | 뉴스·평판 수집 + LLM 감성분석 | 상동. ai 와 파이프라인 성격은 겹치나 데이터 도메인이 다름 |

→ C그룹 5개는 "임베디드 파이낸스 사업부(loan/investment)가 신용·투자 심사를 하려면 외부 리서치
데이터가 필요하다"는 **동일한 상위 니즈 하나**에서 나온, 서로 다른 외부 공급자를 향한 어댑터
모음이다. 실제 조직이라면 이 5개는 "리서치/데이터플랫폼팀" 한 팀이 맡아도 충분하다 — 5개 서비스로
쪼갤 근거는 팀 경계(⑤)가 아니라 **외부 API 별 장애·쿼터·배치 주기가 서로 독립적이라는 기술적
이유(③④)** 뿐이다. 이것을 "근거 없는 분해"가 아니라 **근거가 약한 것을 알면서 감수한 트레이드
오프**로 이 ADR 에 명시적으로 남긴다.

### 4. 결정 — 구조는 유지, 근거만 소급 고정

- 현재 18서비스+gateway 구조는 변경하지 않는다. 위 A/B/C 분류를 이 ADR 에 고정한다.
- C그룹(financial/economics/market/common-data/company)은 **합병 후보로 명시**하되 지금 당장
  합치지 않는다. 이유: (a) 배치/스트리밍 SLA 가 서로 달라 독립 배포가 실제로 유효한 기술적
  사유가 있고, (b) 이미 구현된 개별 admin 게이트·수집 파이프라인·계약을 깨는 재작업 비용이
  얻는 서사 개선 효과보다 크다.
- 향후 새 서비스 분리를 검토할 때는 이 6축 표를 먼저 채우고, 2축 미만이면 기존 서비스 내부
  패키지로 흡수하는 것을 기본값으로 한다.

## 결과

### 좋아지는 점

- "왜 18개인가"에 대해 데이터 단위가 아니라 6축 프레임워크로 즉답 가능해진다.
- A(강한 경계)와 C(약한 경계)를 스스로 구분해 기록함으로써, "모든 분리가 최선이었다"는 무비판적
  주장 대신 **트레이드오프를 인지하고 선택한 판단력**을 보여준다 — 이것이 이 ADR 의 실제 목적.
- 향후 서비스 추가/통합 논의에 재사용 가능한 의사결정 기준을 확보한다.

### 트레이드오프 / 한계

- 문서만으로 구조를 정당화하는 것이라 코드·배포에는 변화가 없다 — "말로 포장했다"는 인상을 줄
  위험은 여전히 남는다. 이 문서 하나로 끝내지 않고, PORTFOLIO.md/ARCHITECTURE.md 의 위성 서비스
  서술에서 이 ADR 을 인용해 A/B/C 분류를 노출하는 후속 작업이 필요하다.
- C그룹을 합치지 않기로 한 결정은 5개 서비스 각각의 CI/게이트/배포 유지비용을 계속 지불한다는
  뜻이다.
- §1 의 사업 전제는 검증된 실제 요구사항이 아니라 선언된 가정이다 — 실제 도메인 전문가 인터뷰나
  시장 데이터로 대체된 것은 아니다.

## 대안 검토

| 옵션 | 채택? | 이유 |
|---|---|---|
| **구조 유지 + 근거 소급 문서화 (본 결정)** | ✓ | 이미 구현된 이벤트 계약·통합테스트 자산 보존, 비용 대비 서사 개선 효과가 큼 |
| C그룹 5개를 단일 external-data-service 로 통합 | ✗(보류) | 개별 배치 SLA·쿼터 격리라는 실제 기술적 사유가 있어 통합 시 오히려 장애 도메인이 섞임. 다만 팀 경계 근거가 약함은 인지하고 §3 에 기록 |
| 전면 재설계(Team Topologies 순수 원칙으로 서비스 수 축소) | ✗ | 정산·원장·보험·카드에 이미 완성된 이벤트 계약·통합테스트 재작업 비용이 서사 개선 효과 대비 과대 |
