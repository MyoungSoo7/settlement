## 1. 배경과 문제

법인카드 경비 처리는 **영수증과 매입 전표를 대사**해서 성립한다. card-service 의
`ExpenseReceiptMatcher` 가 그 판정을 내리는데, 판정의 입력인 **필드 추출**은 지금 외부 LLM(Gemini)
호출에 얹혀 있다(`ExtractReceiptFieldsPort` ← `GeminiReceiptOcrAdapter`). 포트 주석이 스스로
"AI 비전 OCR 구현 교체 지점"이라고 밝히지만, **바꿔도 되는지를 판정할 방법이 없었다.**

| 문제                   | 구체적 손상                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **판정 근거 부재**     | "우리 걸로 바꾸자"를 주장할 숫자가 없다 — 정확도조차 측정된 적이 없었다                  |
| **정확도라는 오지표**  | 총액 일치율이 올라도 운영 비용은 나빠질 수 있다. 실제로 갈리는 건 최종 대사 판정이다     |
| **가용성이 남의 손**   | 벤더 503 이 그대로 경비 업로드 실패가 된다                                              |
| **영수증 외부 전송**   | 영수증에는 상호·금액·카드번호 일부가 찍힌다 — 매 건이 외부로 나간다                     |
| **지연**               | 업로드 화면에서 사람이 기다리는 시간이다                                                |

이 서비스는 **그 자리에 꽂을 자체 구현**과, **바꿔도 되는지를 숫자로 판정하는 하네스**다. 핵심 설계
판단은 하나다 — **정확도가 아니라 운영 판정과 그 비용으로 채점한다.**

## 5. 핵심 유스케이스

### UC-1. 프로바이더를 바꿔 교체 여부를 판정한다

1. `build` 로 합성 골든셋을 만든다(기본 40건 요청, 현재 저장본 **35건**, 시드 `20260821`).
2. `run --provider {gemini|local|local+prep}` 로 프로바이더별 추출을 돌린다.
3. 각 추출을 **운영과 같은 대사 규칙**에 통과시켜 판정을 얻는다.
4. 정답 판정과 대조해 혼동행렬·가중 오류비용·치명 건수·지연을 낸다.
5. 리포트는 `build/reports/{provider}.json|txt` 로 저장된다(재생성 산출물, git 미추적).

### UC-2. 못 읽은 값을 지어내지 않고 끊는다

1. 총액은 대사의 근거다. 파서가 총액을 확정하지 못하면 **부분 결과를 만들지 않고** `ParseFailed`.
2. API 는 이를 **503** 으로 돌려준다 — Java 쪽 `CARD_RECEIPT_OCR_UNAVAILABLE` 과 같은 계약.
3. 거래일은 다르다. 못 읽으면 `null` 로 내보내고, 대사 규칙이 이를 `NEEDS_REVIEW` 로 흘린다 —
   **사람에게 보내는 것이 설계된 안전 경로**이기 때문이다.

### UC-3. 무엇이 총액인지 세 가지 근거로 고른다

영수증에는 금액이 여럿 찍힌다(품목·소계·할인·공급가액·부가세·합계). 파서는 이 순서로 고른다.

1. **구조 검증** — `공급가액 + 부가세 = 합계` 를 만족하는 조합이 있으면 그 합이 총액이다.
   OCR 점수와 **독립인 근거**라 신뢰도를 올릴 자격이 있다(**+0.15**).
2. **글자 크기** — 합계 줄은 큰 폰트다. 다만 추측이므로 **벌점 −0.25**.
3. 둘 다 실패하면 **끊는다**(503).

| 시나리오          | 정답 판정                   |
| ----------------- | --------------------------- |
| `CLEAN`           | `MATCHED`                   |
| `NEXT_DAY`        | `MATCHED` (±1일이 흡수)     |
| `NO_DATE`         | `NEEDS_REVIEW`              |
| `AMOUNT_TAMPERED` | `MISMATCHED`                |
| `STALE_DATE`      | `MISMATCHED`                |

촬영조건: `PRISTINE` · `FADED` · `CRUMPLED` · `SKEWED` · `LOW_LIGHT` · `LOW_RES` · `GLARE`.
3건에 1건은 할인·포인트가 붙어 소계·할인·공급가액·부가세·합계가 함께 찍힌다(금액 후보 다중 축).

```json
{"merchantName": null, "transactionDate": "2026-03-09", "totalAmount": "64100",
 "confidence": "0.8161", "fieldConfidence": {"amount": 0.8816, "date": 0.8161},
 "amountMethod": "structural", "model": "rapidocr+prep"}
```

| ---- | ------------------------------------------- |

**하네스가 잡아낸 것 2건** — 정확도 한 줄만 봤으면 놓쳤을 판단들:

1. **전처리는 정확도를 올리고 손실을 키웠다.** 총액 판독 67.6% → 79.4% 인데 가중 오류비용은
   57 → 79 로 악화(치명 1 → 2건). 더 자신 있게 읽은 값이 임계를 넘어 종결로 갔기 때문이다.
   `largest` 벌점을 넣고 나서야 55(치명 1건)로 내려왔다.
2. **날짜 정규식이 실제 OCR 출력을 통째로 놓치고 있었다.** RapidOCR 은 공백을 먹어
   `2026/03/1900:52` 로 붙이고 앞에 잡음 숫자를 더하기도 한다. 양끝을 `(?<!\d)`/`(?!\d)` 로
   막아 둔 탓에 거래일 판독률이 20.6% 였다 — 느슨하게 고쳐 61.8%.

**baseline 의 치명 오류** — 반사광에 덮인 거래일을 Gemini 가 `2020-08-11` 로 읽고 **신뢰도 0.98** 을
붙였다(정답 `2026-03-11`). 신뢰도가 추출 전체에 대한 스칼라 하나라서 쉬운 필드(총액)의 확신이 어려운
필드(거래일)의 불확실성을 덮었다. 자체 구현은 같은 케이스에서 총액은 구조 검증으로 정확히 읽고
날짜는 `null` 로 내보낸다 — 판정이 종결이 아니라 리뷰로 흐른다(비용 25 → 1).

## 12. 역산에서 드러난 격차

### G-1. 아무도 이 서비스를 부르지 않는다 — 최상위

`POST /extract` 는 존재하지만 **호출자가 없다.** compose·gateway·CI·Dockerfile 어디에도 없고,
card-service 의 `ExtractReceiptFieldsPort` 구현은 여전히 `GeminiReceiptOcrAdapter` 하나뿐이다.
즉 **운영 경로는 Phase 0 baseline 그대로**이며, 이 저장소의 실측 표는 "무엇을 바꾸면 어떻게 되는가"
이지 "지금 무엇이 벌어지고 있는가"가 아니다. 다른 폴리글랏 7종은 최소한 `polyglot-ci.yml` 에
들어가 있는데 이 서비스는 그것도 없어, **CI 가 이 코드를 한 번도 돌리지 않는다.**

### G-2. 정확도 격차가 아직 크다 — 리뷰 큐 범람

판정 일치율 42.9% vs 88.6%. 격차의 대부분은 리뷰 큐 유입률(62.9% vs 17.1%)에서 온다. OCR 토큰
점수는 "이 글자를 이렇게 읽었다"는 확신이지 "이 값이 총액이다"라는 확신이 아니라, 운영 임계 0.80 과
**스케일이 맞지 않는다.** 현 상태로 교체하면 리뷰어 부담이 3.7배가 된다 — Phase 2 가 풀 문제다.

### G-3. `fieldConfidence` 를 받을 곳이 없다

이 서비스의 존재 이유(G5)인 필드별 신뢰도를 서버는 내보내지만, Java `ExtractReceiptFieldsPort` 의
`ExtractedReceipt` 는 **스칼라 `confidence` 하나만 받는다.** 즉 지금 교체해도 baseline 의 치명
오류 패턴(쉬운 필드의 확신이 어려운 필드를 덮음)은 Java 경계에서 그대로 재현된다. 포트 시그니처
변경이 선행되어야 한다.

### G-4. 골든셋이 합성이고 35건이다

렌더러의 글자는 완벽한 디지털 글리프라 실제 감열지의 번짐·인쇄 불량을 흉내만 낸다. 문서가 이
한계를 명시하고 있으나(BR-9), **35건에서 "치명 1건" 은 통계적으로 0건과 2건을 구분하지 못한다.**
한국 카드 영수증 공개 라벨셋이 사실상 없어 실물 셋 확보가 별도 과제로 남아 있다.

### G-5. `build --count 40` 인데 저장본이 35건이다

CLI 기본 생성 수량은 40 인데 추적된 `data/goldenset.json` 은 `count: 35` 다(시나리오 5 × 조건 7의
정확한 교차). 리포트도 전부 35건 기준이다. 재생성 시 기본값으로 돌리면 **골든셋이 조용히 바뀌어**
과거 리포트와 비교 불가가 된다 — 저장본을 만든 인자 조합이 코드나 데이터에 기록돼 있지 않다.

### G-6. 판정 스칼라 임계가 하드코딩된 운영값에 묶여 있다

채점은 `--threshold`(기본 0.80)를 받지만, 이 값은 card-service 의 운영 설정에서 온 값이다. 양쪽이
따로 움직이면 하네스 점수가 운영과 어긋난다 — 프롬프트는 드리프트 가드(FR-13)가 있는데 **임계값에는
같은 가드가 없다.**
