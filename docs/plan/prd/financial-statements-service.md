## 1. 배경과 문제

기업 신용평가(loan)와 투자 판단(investment)은 **상장사의 재무 숫자**를 입력으로 받는다. 그런데 그 숫자를
각 서비스가 DART 에서 직접 받아오면 세 가지가 무너진다.

| 문제              | 구체적 손상                                                             |
| ----------------- | ----------------------------------------------------------------------- |
| **비율 정의 산재** | 부채비율을 어떤 분모로 나눌지가 서비스마다 달라 같은 회사가 다르게 평가된다 |
| **결측 처리 제각각** | 분모가 0/null 일 때 0 으로 둘지 제외할지가 통일되지 않는다             |
| **수집 중복**     | DART 키·쿼터·연결/별도 구분 로직이 N벌로 흩어진다                       |

financial-statements-service 는 재무제표를 한 곳에서 수집·보관하고, **비율은 저장하지 않고 계산해서**
서빙한다. 핵심 설계 판단은 하나다 — **모르는 것을 0 으로 만들지 않는다.**

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 재무 비율의 정의를 단일 출처로 고정 | 5개 비율이 도메인 한 곳에서만 계산된다 |
| G2 | 계산 불가를 값으로 위장하지 않는다 | 분모가 없거나 0 이면 `null`(N/A) |
| G3 | 원본 숫자를 보존한다 | 비율은 저장하지 않는다 — 원본만 저장 |
| G4 | 조회는 개방, 수집은 통제 | GET 공개 / `/admin` 내부 키 |

### 2.2 비목표

| # | 비목표 | 이유 |
|---|---|---|
| N1 | **PER·PBR 등 시장가 결합 지표** | 시세는 market-service 소관. 조인은 소비측 몫 |
| N2 | 비율 저장 | 원본과 어긋날 수 있다. 계산은 읽기 시점 |
| N3 | 샘플 데이터 시딩 | 실수집 전용으로 전환됨 — 가짜 숫자가 신용평가에 들어가면 안 된다 |
| N4 | 재무 예측 | 별도 서비스(forecast) 책임 |

| 영역 | 기능 |

## 5. 핵심 유스케이스

### UC-1. 신용평가가 재무 비율을 입력으로 받는다

1. loan-service 가 `GET /api/financial/companies/{code}` 계열로 최신 재무를 받는다.
2. 응답에 5개 비율이 포함된다 — **저장된 값이 아니라 그 자리에서 계산된 값**이다.
3. 분모가 없거나 0 인 비율은 `null` 로 온다. 소비측은 이를 "0%"가 아니라 **"판단 불가"** 로 다뤄야 한다.

> 실제로 investment-service 의 3축 점수는 이 `null` 을 0점(보수적)으로 환산한다 — 그 환산 책임이
> 소비측에 있다는 것이 이 서비스의 계약이다.

### UC-2. 주간 수집이 최신 공시를 반영한다

1. 일요일 04:00 에 재무제표 수집이 돈다.
2. 매월 1일 05:00 에 기업 목록이 갱신된다(신규 상장·상장폐지 반영).
3. 재수집은 같은 (기업, 기간, 구분) 키를 대체한다.

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 영업이익률 = 영업이익/매출 × 100 | `FinancialStatement.operatingMargin` |
| FR-2 | 순이익률 = 당기순이익/매출 × 100 | `netMargin` |
| FR-3 | 부채비율 = 부채총계/자본총계 × 100 | `debtRatio` |
| FR-4 | 자기자본비율 = 자본총계/자산총계 × 100 | `equityRatio` |
| FR-5 | ROA = 당기순이익/자산총계 × 100 | `roa` |
| FR-6 | 분모가 null·0 이면 결과는 `null` | 공통 `ratio()` 헬퍼 |
| FR-7 | 비율은 저장하지 않는다 | 원본 컬럼만 영속 |
| FR-8 | 연결/별도를 구분해 저장·조회한다 | `FsDivision` |
| FR-9 | 조회는 인증 없이, 수집은 내부 키로만 | `AdminApiKeyFilter` |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **비율은 파생값** — 저장하지 않고 계산한다. 원본이 정본이다 | `FinancialStatement` 계산 메서드 5종 |
| BR-2 | **N/A 는 null** — 0 으로 환산하지 않는다. 환산 책임은 소비측 | 공통 `ratio()` |
| BR-3 | **시장가와 섞지 않는다** — PER/PBR 은 이 서비스가 만들지 않는다 | 범위 경계(market-service 와 대칭) |
| BR-4 | **실수집 전용** — 샘플 시드를 제거했다. 신용평가에 가짜 숫자가 들어가면 안 된다 | 시드 제거 이력 |

## 12. 역산에서 드러난 격차

### G-1. `null` 의 의미가 소비측에서 갈린다

BR-2 는 "판단 불가"를 `null` 로 표현한다. 그런데 investment-service 는 이를 **0점**으로 환산하고
(보수적 판단), loan-service 가 같은 규칙을 쓰는지는 이 역산 범위에서 확인하지 않았다. 두 소비측이
다르게 환산하면 **같은 회사가 서비스마다 다른 평가**를 받는다.

### G-2. 비율 정의가 문서보다 코드에 있다

5개 비율의 분자·분모가 도메인 메서드에만 있고, API 응답 스키마나 문서에 수식이 명시돼 있는지는
확인하지 않았다. 소비측이 "부채비율"을 자기 정의로 오해할 여지가 남는다.

### G-3. 결측이 흔한 데이터인데 결측률 관측이 없다

DART 공시는 항목 누락이 잦다. 그런데 "이 기업의 비율 5개 중 몇 개가 `null` 인가"를 집계·관측하는
경로가 없다. 신용평가 입력의 품질이 조용히 나빠져도 드러나지 않는다.

### G-4. 수집 주기와 공시 주기가 어긋난다

재무제표 수집은 주간(일요일)인데 공시는 분기 마감 후 특정일에 몰린다. 최악의 경우 **최대 6일** 늦게
반영된다. 실시간성이 필요한 판단(대출 심사)에 이 지연이 허용되는지는 문서에 없다.

### G-5. 도메인 예외가 generic 이다

위성 공통 — 필수값 검증이 `IllegalArgumentException` 이며 `OO-DOMAIN-GENERIC-IAE` 게이트 대상 밖이다.
