## 1. 배경과 문제

CEO 투자 화면은 종목 현재가를 보여줘야 하는데, `market-service` 는 **일별 종가**를 서빙하는 배치형
조회 서비스다. 화면이 초 단위로 갱신되려면 다른 성격의 서비스가 필요하다.

| 문제                    | 구체적 손상                                                                |
| ----------------------- | -------------------------------------------------------------------------- |
| **폴링의 비용**         | 브라우저가 1초마다 REST 를 때리면 커넥션·DB 부하가 구독자 수에 비례해 폭증 |
| **JVM 의 커넥션 비용**  | 장기 유지 커넥션 수천 개는 스레드 모델과 궁합이 나쁘다                     |
| **실데이터 부재**       | 실시간 체결 피드를 살 수 없으면 화면이 아예 못 뜬다                        |

market-stream-service 는 **종목당 goroutine 하나가 틱을 만들고 구독자에게 팬아웃하는** Go 서비스다.
핵심 설계 판단은 하나다 — **구독자가 0이면 아무 것도 돌지 않는다.**

## 4. 제품 범위 — 기능 맵

| 영역       | 기능                                                              |
| ---------- | ----------------------------------------------------------------- |
| 스트리밍   | SSE `/stream/{code}`(외부 노출) · WS `/ws/{code}`(내부만)         |
| 팬아웃     | 종목별 단일 생산자 + 구독자별 버퍼 채널, drop-oldest              |

| 운영       | `/healthz`, graceful shutdown 10초, distroless non-root           |

## 5. 핵심 유스케이스

### UC-1. 화면이 종목 현재가를 1초마다 받는다

1. 브라우저가 `EventSource('/api/market-stream/stream/005930')` 를 연다.
2. 게이트웨이가 `RewritePath` 로 프리픽스를 벗겨 `/stream/005930` 으로 전달한다.
3. 서버가 `: connected` 주석을 즉시 내보내 연결을 확정시킨 뒤 구독한다.
4. 이 종목의 첫 구독자면 quote loop goroutine 이 시작되고, `event: tick` 프레임이 1초마다 흐른다.
5. 탭을 닫으면 요청 컨텍스트가 취소되고 구독이 해제된다. 마지막 구독자였다면 loop 도 멈춘다.

### UC-2. 느린 클라이언트가 다른 구독자를 굶기지 않는다

1. 브로드캐스트는 락을 잡고 채널 스냅샷만 뜬 뒤 **락을 놓고** 송신한다.
2. 구독자 버퍼(기본 16)가 가득 차면 가장 오래된 틱을 버리고 최신 틱을 넣는다.
3. 실시간 가격 스트림은 완전성보다 **최신성**이 가치라는 판단이다.

### UC-3. 실 종가를 기준선으로 삼는다

1. `MARKET_STREAM_SOURCE=polling`(compose 기본)이면 `PollingSource` 가 `SimulatedSource` 를 감싼다.
2. quote loop 시작 시 `GET {MARKET_BASE_URL}/api/market/stocks/{code}/series?from={30일전}` 을 호출한다.
3. 시계열 마지막 점의 종가를 base 로 채택한다. 요청 실패·비200·빈 시계열·0 이하 값이면 시뮬레이션 base 로 폴백한다 — **스트림은 절대 죽지 않는다.**

## 6. 기능 요구사항

| FR   | 요구사항                                                      | 강제 지점                              |
| ---- | ------------------------------------------------------------- | -------------------------------------- |
| FR-1 | 종목당 quote loop 는 정확히 1개                               | `Hub.Subscribe` 첫 구독자 분기         |
| FR-2 | 마지막 구독자가 떠나면 loop 를 취소하고 맵에서 제거한다       | `Hub.unsubscribe`                      |
| FR-3 | unsubscribe 는 여러 번 호출해도 안전하다                      | `sync.Once`                            |
| FR-4 | 송신은 절대 블로킹하지 않는다                                 | `select`+`default` 2단(폐기 후 재시도) |
| FR-5 | 빈 종목코드는 400                                             | SSE·WS 핸들러 공통                     |
| FR-6 | 틱 가격은 base 대비 ±5% 밴드로 클램프된다                     | `SimulatedSource.Next`                 |
| FR-7 | 같은 (seed, code) 는 같은 틱 시퀀스를 만든다                  | `seed ^ fnv64a(code)`                  |
| FR-8 | 타임스탬프는 UTC RFC3339 밀리초                               | `NewTick`                              |
| FR-9 | 종료 시 10초 안에 우아하게 닫는다                             | `srv.Shutdown` + `Hub.Shutdown`        |

## 12. 역산에서 드러난 격차

### G-1. 화면에 보이는 "실시간 시세"는 실제 체결가가 아니다 ★

`polling` 모드에서도 실데이터는 **base 가격 하나뿐**이고, 초 단위 틱은 전부 `SimulatedSource` 의 난수 워크다
(base 대비 ±5% 밴드, 틱당 ±1%). 프론트 `LiveQuoteTicker` 는 이 값을 CEO 투자 화면에 현재가로 표시한다.
코드 주석과 `polyglot-services.md` 는 이 사실을 명시하지만, **화면과 API 응답에는 시뮬레이션임을 알리는
표식이 없다.** 투자 의사결정 화면에 붙는 숫자로서 가장 큰 제품 리스크다.

### G-2. 폴링 주기가 실질적으로 "구독 시작 시 1회"다 ★

`runQuoteLoop` 은 `BasePrice` 를 **루프 진입 전 한 번만** 호출하고, 이후 틱은 `SimulatedSource.Next` 가
내부에 기억한 base 로 계속 돈다. `MARKET_STREAM_POLL_INTERVAL`(기본 60초)은 `shouldPoll` 의 레이트 리밋일
뿐, 루프가 도는 동안 base 가 갱신되는 경로가 없다. 즉 브라우저가 한 종목을 몇 시간 열어 두면 그 종목의
기준가는 **연결 시점의 종가에 고정**된다. 설정 이름이 약속하는 동작과 실제가 다르다.

### G-3. 구독 상한이 없다

종목 수·구독자 수·클라이언트당 연결 수에 어떤 제한도 없다. 인증도 레이트리밋도 없으므로(N3 은 인증만
비목표로 선언), 임의 종목코드로 연결을 반복하면 **새 goroutine 과 맵 엔트리가 무제한 생성**된다. 현재
방어는 게이트웨이 앞단(nginx)·네트워크 경계뿐이다.

### G-4. 종목코드가 검증되지 않는다

`/stream/ZZZZZZ` 같은 존재하지 않는 코드도 정상적으로 스트림을 만든다 — 폴링이 실패하면 기본 base
70,000원으로 그럴듯한 가격이 흐른다. 클라이언트는 "없는 종목"과 "값이 흐르는 종목"을 구분할 수 없다.

### G-5. 메트릭 노출 경로가 없다

`Hub.ActiveCodes()`·`SubscriberCount()` 는 "for tests and metrics" 라고 적혀 있지만 이를 내보내는
엔드포인트가 없다(`/metrics` 부재). 폴리글랏 Kotlin 2종은 Prometheus 레지스트리를 갖는데 Go 2종은 없다.
운영 중 몇 명이 붙어 있는지, drop-oldest 로 틱이 얼마나 버려지는지 관측할 방법이 전무하다.

### G-6. 틱 폐기가 조용하다

버퍼 초과 폐기(BR-2)는 로그도 카운터도 남기지 않는다. 클라이언트는 값이 튀는 것으로만 인지할 수 있고,
서버는 그 사실을 전혀 모른다. notification 의 같은 상황(메일박스 초과)이 `warn` 을 남기는 것과 대조된다.

### G-7. WebSocket 이 Origin 을 검증하지 않는다

`websocket.AcceptOptions{InsecureSkipVerify: true}` — 코드 주석이 "TODO: constrain OriginPatterns for
production" 이라고 명시한다. 게이트웨이에 `/ws/**` 를 올리지 않은 것이 유일한 방어이며, 서비스 포트에
직접 도달 가능한 위치에서는 임의 오리진이 붙을 수 있다.

### G-8. 헬스체크를 컨테이너가 못 돈다

compose 주석이 적시하듯 distroless 이미지에는 셸이 없어 `healthcheck` 를 정의하지 못했다. `/healthz` 는
구현돼 있으나 **compose 는 이 서비스의 건강을 판단하지 않는다** — `depends_on` 대상으로도 쓸 수 없다.
