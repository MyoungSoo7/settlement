## 1. 배경과 문제

공공데이터포털(data.go.kr)에는 사업에 쓸 만한 데이터셋이 수백 개 있다. 그런데 **하나 쓸 때마다 코드를
짜야 한다면** 시도 비용이 너무 커서 "일단 붙여보자"가 성립하지 않는다.

| 문제               | 구체적 손상                                                                |
| ------------------ | -------------------------------------------------------------------------- |
| **시도 비용**      | 데이터셋 하나 붙이는 데 어댑터·엔티티·마이그레이션이 필요하면 실험이 죽는다 |
| **파싱 규칙 산재** | 포털 응답의 표준 봉투(header/body/items)를 서비스마다 다시 해석한다        |
| **원문 소실**      | 파싱해서 정규화 저장하면, 나중에 다른 필드가 필요할 때 다시 수집해야 한다  |

common-data-service 는 **데이터소스를 등록하면 코드 변경 없이 수집되는** 범용 커넥터다. 핵심 설계 판단은
하나다 — **해석하지 않고 원문을 보존한다.**

## 2. 목표 / 비목표

### 2.1 목표

| # | 목표 | 성공 기준 |
|---|---|---|
| G1 | 데이터셋 추가가 배포 없이 가능하다 | `data_sources` row 등록만으로 수집·조회된다 |
| G2 | 재수집이 데이터를 부풀리지 않는다 | `(source, record_key)` 자연키 UPSERT |
| G3 | 나중에 다른 필드가 필요해도 재수집이 필요 없다 | 응답 아이템 JSON **원문 보존** |
| G4 | 등록이 내부망 공격 통로가 되지 않는다 | 내부·사설·링크로컬 대상 등록 거부 |

### 2.2 비목표 (의도적으로 하지 않는 것)

| # | 비목표 | 이유 |
|---|---|---|
| N1 | 데이터셋별 도메인 해석 | 범용 커넥터의 책임이 아니다. 해석은 소비측 몫 |
| N2 | 정규화 스키마 저장 | 데이터셋마다 스키마가 다르다 — 원문 보존이 범용성의 전제 |
| N3 | 자동 스케줄 수집 | 현재는 관리 트리거 기반(→ G-3) |
| N4 | 인증된 사용자별 접근 제어 | 공개 데이터라 조회는 공개, 등록만 통제 |

## 3. 사용자

| 사용자 | 무엇을 위해 쓰는가 |
|---|---|
| **데이터 실험자/운영자** | 새 공공데이터셋을 등록해 바로 수집·확인 |
| **소비 서비스** | 수집된 원문을 읽어 자기 도메인으로 해석 |
| **외부/프론트** | 인증 없이 수집 데이터 조회 |

## 4. 제품 범위 — 기능 맵

| 영역 | 기능 |
|---|---|
| 데이터소스 | 등록·조회(엔드포인트·기본 파라미터·키 필드·공급자) |
| 수집 | 관리 트리거로 실행, 표준 봉투 파싱 후 원문 저장 |
| 조회 | 소스 목록, 소스별 레코드 조회 |
| 보안 | 등록 시 SSRF 차단, 관리 API 키 게이트 |
| 운영 | 감사 로그(파티션드), 파티션 러너 |

## 5. 핵심 유스케이스

### UC-1. 새 데이터셋을 등록해 바로 수집한다

1. 운영자가 `POST /admin/commondata/sources` 로 소스를 등록한다(코드·엔드포인트·기본 파라미터·키 필드).
2. 등록 시 **SSRF 검사**가 돈다 — 내부/사설/루프백/링크로컬(메타데이터 `169.254.169.254` 포함) 대상이면 거부.
3. 수집을 트리거하면 표준 봉투를 파싱해 아이템별로 저장한다.
4. 코드 변경·배포는 없었다.

### UC-2. 재수집해도 레코드가 늘지 않는다

1. `record_key` 는 등록 시 지정한 keyFields 값들의 조인, 없으면 payload SHA-256 이다.
2. `(source_id, record_key)` UNIQUE 로 UPSERT 된다.
3. 재수집은 payload·`collected_at` 갱신으로 흡수된다 — 행이 늘지 않는다.

### UC-3. 소비측이 나중에 다른 필드를 쓴다

1. 저장된 `payload` 는 응답 아이템 **JSON 원문**이다.
2. 처음에 안 쓰던 필드가 필요해져도 재수집 없이 기존 레코드에서 읽는다.

## 6. 기능 요구사항

| FR | 요구사항 | 강제 지점 |
|---|---|---|
| FR-1 | 데이터소스는 코드(`code`)로 유일하다 | `uq_ds_code` |
| FR-2 | 레코드는 `(source_id, record_key)` 로 유일하다 | `uq_dr_source_key` |
| FR-3 | `payload` 는 필수이며 원문을 보존한다 | `DataRecord` 검증 + 도메인 주석 |
| FR-4 | `record_key` 는 keyFields 조인 또는 payload 해시로 결정한다 | 수집 서비스 |
| FR-5 | 등록 엔드포인트가 내부·사설·링크로컬이면 거부한다 | `DataSourceAdminService` SSRF 검사 |
| FR-6 | 조회는 인증 없이, 등록·수집은 내부 키로만 | `AdminApiKeyFilter` |
| FR-7 | 관리 조작은 감사 로그에 남는다 | `audit_logs`(파티션드) |

## 7. 도메인 규칙 (BR)

| BR | 규칙 | 근거 |
|---|---|---|
| BR-1 | **원문 보존** — 파싱은 저장 위치를 정하기 위한 것이지 데이터를 바꾸기 위한 것이 아니다 | `DataRecord.payload` |
| BR-2 | **자연키 멱등** — 재수집은 갱신이지 추가가 아니다 | `uq_dr_source_key` |
| BR-3 | **등록은 통제, 조회는 개방** — 공개 데이터이므로 읽기를 막을 이유가 없다. 위험은 *등록*에 있다 | 키 게이트 + SSRF 검사 |
| BR-4 | **해석하지 않는다** — 데이터셋의 의미는 소비측이 정한다 | 범용 커넥터 설계 |

## 12. 역산에서 드러난 격차

### G-1. 실수집이 검증되지 않았다

`DATA_GO_KR_API_KEY` 미보유로 **실제 포털 응답으로 수집을 돌려본 적이 없다.** 표준 봉투 파싱·키 추출은
테스트 픽스처 기준으로만 검증됐다. 실제 데이터셋의 봉투 변형(항목 누락, 배열/단일 혼재)에서 어떻게
동작하는지는 미지수다.

### G-2. SSRF 검사가 등록 시점 1회다

등록 시 호스트·IP 를 검사하지만, **DNS 재바인딩**(등록 후 A 레코드가 내부 IP 로 바뀌는 경우)이나
리다이렉트 추적은 이 검사 밖이다. 수집 시점 재검증 여부는 역산 범위에서 확인하지 않았다.

### G-3. 자동 수집이 없다

수집이 관리 트리거로만 돈다. market·economics 는 일 1회 스케줄러를 갖는데 여기만 없어, 등록해둔
데이터소스가 **누가 부르지 않으면 영원히 갱신되지 않는다.**

### G-4. 원문 보존의 대가가 조회 성능에 있다

`payload` 가 JSON 원문이라 특정 필드로 거르려면 소비측이 전부 읽어 파싱해야 한다. 인덱스는
`(source_id, collected_at)` 뿐이며 payload 내부 값으로는 검색할 수 없다.

### G-5. 도메인 예외가 generic 이다

SSRF 거부·필수값 검증이 `IllegalArgumentException` 이다. 보안 거부와 입력 오류가 같은 타입이라
호출측이 구분하려면 메시지를 봐야 한다.
