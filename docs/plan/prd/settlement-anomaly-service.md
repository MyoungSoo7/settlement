## 1. 배경과 문제

정산·지급 레코드는 하루 수만 건이다. **"이상하다"의 정의를 규칙으로만 쓰면** 두 방향으로 실패한다.

| 문제                | 구체적 손상                                                                |
| ------------------- | -------------------------------------------------------------------------- |
| **임계값 지옥**     | "100만원 초과 경고"는 커피숍엔 과하고 여행사엔 무의미하다                 |
| **조합 이상 누락**  | 금액·시간·빈도가 각각은 정상인데 **조합**이 비정상인 건은 규칙이 못 잡는다 |
| **설명 불가**       | ML 점수만 주면 운영자가 왜 걸렸는지 몰라 조치할 수 없다                   |

settlement-anomaly-service 는 **해석 가능한 통계 계층과 다변량 ML 계층을 섞어 0~1 점수와 사람이 읽는 근거를
함께 내는** 스코어러다. 핵심 설계 판단은 하나다 — **가맹점 자기 기준선과 비교한다.**

## 5. 핵심 유스케이스

### UC-1. 커피숍의 18만원 지급을 잡는다

1. `M-COFFEE` 의 학습 기준선은 중앙값 4,500원 수준이다.
2. 180,000원은 가맹점 MAD 기준 z 가 포화 구간을 넘어 통계 점수 ≈ 1.0.
3. IsolationForest 도 다변량 이상으로 표시하면 근거가 하나 더 붙고 앙상블에 동의 보너스가 더해진다.
4. 결과: `{id, anomalyScore, isAnomaly: true, reasons: ["amount robust z-score …", "isolation-forest flagged …"]}`.

### UC-2. 표본이 부족한 가맹점을 전역 기준으로 본다

1. `base.count < 3` 이거나 MAD 가 0이면 가맹점 기준선을 믿지 않는다.
2. 전역 중앙값·MAD 로 폴백하고 근거 문자열에 `global` 이라고 적는다.

### UC-3. 새벽 지급을 가중한다

1. 00:00~04:59 는 정산/지급 활동의 오프아워로 간주해 0.4 를 준다.
2. 단독으로는 임계(0.7)를 넘지 못한다 — 다른 신호와 함께여야 걸린다(동시 2개 이상이면 +0.15).

## 7. 도메인 규칙 (BR)

| BR   | 규칙                                                                                          | 근거                        |
| ---- | --------------------------------------------------------------------------------------------- | --------------------------- |
| BR-1 | **기준은 가맹점 자신이다** — 절대 금액이 아니라 자기 분포에서 얼마나 벗어났는가              | `_stat_score_and_reasons`   |
| BR-2 | **표본이 얕으면 믿지 않는다** — 3건 미만이면 전역 기준으로 내려간다                           | `base.count >= 3` 가드      |
| BR-3 | **둘 중 하나만 확신해도 이상이다. 둘 다면 더 이상이다** — 가중합 + 동의 보너스                | 앙상블 블렌딩               |
| BR-4 | **점수에는 근거가 따라붙는다** — 통계 계층이 사람이 읽는 문자열을 만든다                      | `reasons`                   |
| BR-5 | **한 건의 나쁜 레코드가 배치를 죽이지 않는다** — 파싱 실패는 폴백                             | `_parse_hour` 주석          |

## 12. 역산에서 드러난 격차

### G-1. 환경변수가 실제로는 프로세스당 1회만 읽힌다 ★

`Settings` 는 `@dataclass(frozen=True)` 이고 필드 기본값이 `_get_int("PORT", 8121)` 같은 **함수 호출**이다.
파이썬은 기본값을 **클래스 정의 시점에 한 번** 평가하므로, `get_settings()` 가 매번 새 인스턴스를 만들어도
값은 import 시점에 굳은 그대로다. `get_settings` 의 독스트링은 "Not cached so tests can monkeypatch env vars
and rebuild" 라고 적혀 있지만 **그 약속이 지켜지지 않는다** — 임포트 후 `ANOMALY_THRESHOLD` 를 바꿔도
반영되지 않는다. (대조: `forecast-service` 의 `load_settings()` 는 호출 시마다 `os.getenv` 를 읽어 정상 동작한다.)

### G-2. `merchant_freq` 피처가 학습·추론에서 다른 의미를 갖는다 ★

`build_feature_matrix` 의 `merchant_freq` 는 **"이 배치 안에서 그 가맹점의 건수"** 다. 학습은 가맹점당 60건
배치로 돌아 freq≈60 이지만, 실사용에서 1~수 건을 스코어링하면 freq=1~3 이 된다. IsolationForest 입장에서는
모든 추론 레코드가 학습 분포에서 크게 벗어난 값을 갖는 셈이라 **호출 배치 크기가 이상 점수를 좌우한다.**
가맹점 기준선(`baselines`)은 학습 시점 통계를 쓰는데 이 피처만 배치 통계를 쓰는 비대칭이다.

### G-3. 모델이 가짜 데이터로만 학습돼 있다

기본 학습셋은 `sample_data.py` 가 생성하는 5개 가상 가맹점(`M-COFFEE`·`M-GROCER`…)의 합성 레코드다.
실제 `settlement_db` 데이터를 끌어오는 경로가 없다(N4 는 pull 을 비목표로 선언). 따라서 실 정산 건을
`/score` 로 보내면 **학습된 가맹점 기준선이 하나도 매칭되지 않아 전역 폴백으로만 동작한다**(BR-2) — G1 의
"절대 임계값을 쓰지 않는다"가 실질적으로 무력화된다.

### G-4. `/train` 이 무인증으로 전역 상태를 덮어쓴다

`POST /train` 은 인증이 없고, 호출 즉시 `AnomalyService.detector` 를 교체한다. 임의의 요청 하나가 이후
모든 스코어링의 기준선을 바꿀 수 있다. `/score`·`/score/demo` 도 동일하게 인증이 없다.

### G-5. 학습 상태가 워커·레플리카마다 다르다

모델은 프로세스 메모리에 있다. uvicorn 워커를 늘리거나 레플리카를 두면 각자 다른 시점의 학습 상태를 갖고,
`/train` 은 요청을 받은 워커에만 적용된다. 같은 레코드가 어느 워커에 걸리느냐에 따라 다른 점수를 받는다.

### G-6. IsolationForest 점수가 학습 범위 밖에서 포화한다

정규화는 학습셋 `decision_function` 의 min/max 로 클램프한다. 학습 때 본 것보다 더 극단적인 레코드는 전부
1.0 으로 뭉개져 **"매우 이상"과 "극도로 이상"을 구분하지 못한다.**

### G-7. 이 서비스를 호출하는 곳이 없다

compose 정의도, 게이트웨이 라우트도, 호출하는 Java 서비스도 없다. `operation-service` 가 자체 이상탐지를
갖고 있어(운영 관제 도메인) 이 서비스는 현재 **어떤 실 트래픽도 받지 않는다.**

### G-8. 관측 수단이 로그뿐이다

`/metrics` 도 카운터도 없다. 스코어링 건수·플래그율·학습 시점을 지표로 볼 수 없다.
