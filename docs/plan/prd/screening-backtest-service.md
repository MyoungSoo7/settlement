## 1. 배경과 문제

`investment-service` 는 종목마다 **3분할 매수 + 손절 -7% + 익절 +20%** 라는 매매계획을 제시한다. 그런데
그 규칙이 **과거에 실제로 돈을 벌었는지 아무도 확인하지 않았다.**

| 문제                | 구체적 손상                                                            |
| ------------------- | ---------------------------------------------------------------------- |
| **미검증 규칙**     | 손절/익절 비율의 근거가 "그럴듯함"에 머문다                           |
| **JVM 의 한계**     | 시계열 워크·지표 계산은 pandas/numpy 가 압도적으로 편하다             |
| **재현 불가**       | 규칙을 바꿨을 때 성과가 어떻게 달라지는지 비교할 기준선이 없다        |

screening-backtest-service 는 **같은 매매계획을 과거 종가 시계열에 적용해 수익률·MDD·Sharpe·승률을 내는**
검증 도구다. 핵심 설계 판단은 하나다 — **매매계획 계산을 Java 도메인과 동일하게 재현한다.**

## 5. 핵심 유스케이스

### UC-1. 스크리닝 픽 묶음의 과거 성과를 잰다

1. 호출자가 픽(`stockCode`·`signalDate`·`currentPrice`)과 종목별 종가 시계열, 기간(`horizonDays`), 선택적 예산을 보낸다.
2. 픽마다 매매계획을 계산한다 — 예산이 없으면 가격 레벨만(가중평균 평단), 있으면 구간별 수량을 내림 배분해 체결금액에서 평단을 낸다.
3. 신호일 **이후** 종가를 날짜순으로 정렬해 앞에서부터 걷는다. 익절 도달이면 TAKE_PROFIT, 손절 이탈이면 STOP_LOSS, 기간 안에 둘 다 없으면 마지막 종가로 HORIZON 청산.
4. 거래별 수익률을 순차 복리해 자산곡선을 만들고 포트폴리오 지표를 낸다.

### UC-2. 예산이 부족한 픽을 걸러낸다

1. 구간별 `floor(예산×비중 / 진입가)` 가 모두 0이면 총수량이 0이다.
2. `feasible=false` 와 사유 문자열을 담아 반환하고 **거래 목록에 넣지 않는다** — 지표를 왜곡하지 않는다.

### UC-3. KRX 호가단위를 지킨다

1. 2023-01 개편 기준 6구간 + 최상단(1,000원) 테이블.
2. 진입가·손절가·익절가 모두 **내림**한다 — 존재하지 않는 호가로 계산하지 않는다.

## 12. 역산에서 드러난 격차

### G-1. Java 정책을 복제해 두 구현이 갈라질 수 있다 ★

`trade_plan.py` 모듈 주석이 "Reimplemented faithfully from the investment-service Java domain
(`TradePlanPolicy.java`)" 라고 명시한다. 그런데 **두 구현을 묶는 계약 테스트가 없다.** Java 쪽 비율(0.93/1.20),
구간 비중(30/30/40), 틱 테이블 중 하나라도 바뀌면 파이썬은 그대로 남아 **낡은 규칙을 백테스트하고도 초록불**이
된다. 이 서비스의 존재 이유(BR-1)를 정면으로 무력화하는 위험이다.

### G-2. `MARKET_BASE_URL` 이 선언만 있고 쓰이지 않는다

`Settings.market_base_url` 이 정의돼 있지만 이를 참조하는 코드가 **한 줄도 없다.** 시세는 오직 요청 본문이나
번들 샘플에서 온다. `polyglot-services.md` 도 "선언만 존재 — 실연동 경로 미구현"으로 이 사실을 적고 있다.
설정 존재가 "market-service 와 연동된다"는 오해를 만든다.

### G-3. 종가만 보는 청산이 낙관 편향을 만든다

`simulate_exit` 은 일간 **종가**만 본다. 실제로는 장중 저가가 손절선을 먼저 찍고 종가가 회복해 익절선에
닿는 날이 있는데, 이 모델은 그런 날을 TAKE_PROFIT 으로 기록한다. N4 가 일중 시뮬레이션을 비목표로
선언했으므로 의도된 단순화지만, **결과 수익률이 구조적으로 낙관 쪽으로 치우친다**는 사실은 응답 어디에도
표시되지 않는다.

### G-4. CAGR 의 기간 산정이 합산 보유일이다

`run_backtest` 은 픽별 `holding_days` 를 **더해서** `total_days` 로 넘긴다. 픽들이 동시에 보유된 경우
실제 캘린더 스팬보다 훨씬 큰 값이 되어 연 환산 기간이 과대해지고 **CAGR 이 과소 계산**된다. 픽이 하나뿐일
때만 이 값이 의미를 갖는다.

### G-5. 자산곡선이 순차 전량 배분을 가정한다

`_equity_curve` 는 각 픽을 "포트폴리오 전액을 차례로 투입"한 것으로 복리한다(코드 주석이 MVP 단순화라고
명시). 실제 분산 포트폴리오의 수익률·MDD 와는 다른 수치이며, 픽 순서가 바뀌면 MDD 도 바뀐다.

### G-6. Sharpe 가 연율화되지 않았다

`sharpe` 는 거래별 수익률의 평균/표준편차다(독스트링 명문). 일반적으로 인용되는 연율 Sharpe 와 값의 크기가
달라, 다른 백테스트 결과와 직접 비교하면 오해를 부른다. 응답 필드명은 그냥 `sharpe` 다.

### G-7. 수수료·세금이 없다

거래세·수수료·슬리피지가 전혀 없다(N1, 주석 명문). 3분할 매수 + 청산이면 최소 4회 체결이라 실전 수익률과의
괴리가 작지 않다.

### G-8. 호출자·배선이 없고 인증도 없다

compose 정의, 게이트웨이 라우트, 호출하는 Java 서비스가 모두 없다. 세 엔드포인트 모두 인증이 없다.
현재 이 서비스는 로컬 실행·데모 용도로만 존재한다.
