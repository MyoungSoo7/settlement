## 1. 배경과 문제

CEO 대시보드는 "지금까지 얼마 벌었나"는 보여주지만 **"다음 2주에 얼마가 들어올까"는 못 보여준다.**
정산 매출은 주간 계절성(주말 하락)과 성장 추세가 겹친 시계열이다.

| 문제                | 구체적 손상                                                        |
| ------------------- | ------------------------------------------------------------------ |
| **자금계획 부재**   | 지급 일정을 짜려면 유입 예측이 필요하다                           |
| **계절성 무시**     | 단순 이동평균은 주말 하락을 추세 악화로 오독한다                  |
| **JVM 의 공백**     | Holt-Winters·statsmodels 급 도구가 JVM 생태계에 마땅치 않다       |

forecast-service 는 **날짜가 붙은 시계열을 받아 지정 기간만큼 예측값과 신뢰구간을 돌려주는** 얇은 예측 API 다.
핵심 설계 판단은 하나다 — **데이터가 모자라면 조용히 더 단순한 모델로 내려간다.**

## 5. 핵심 유스케이스

### UC-1. 일별 정산액 120일로 향후 14일을 예측한다

1. 호출자가 `{series:[{date,value}...], horizon, seasonPeriod, model}` 를 보낸다.
2. 날짜 오름차순이 아니면 **422** 로 거절한다 — 정렬을 대신 해주지 않는다.
3. 주기 7이고 표본이 `max(min_seasons×7+1, 2×7+1)` 이상이면 가법 계절 Holt-Winters 로 적합한다.
4. 마지막 두 날짜 간격(일)을 그대로 미래 날짜에 적용한다.
5. `{model, forecast[{date,yhat,lower,upper}], metricsInSample{mape,rmse}}` 를 돌려준다.

### UC-2. 데이터가 모자라면 더 단순한 모델로 내려간다

1. `n < 4` 면 Holt-Winters 를 시도조차 하지 않고 seasonal-naive 로 간다(로그 남김).
2. statsmodels 적합이 예외를 내면 경고 로그 후 역시 seasonal-naive.
3. 모델 라벨이 응답에 그대로 실린다 — `holt_winters_seasonal` / `holt_winters_trend` / `seasonal_naive`.

### UC-3. 계절 주기가 없으면 "마지막 값 반복"이 된다

1. `seasonPeriod` 가 없거나 1이면 seasonal-naive 는 주기 1로 동작한다.
2. 즉 고전적 naive(마지막 값 반복) 예측으로 자연스럽게 축약된다.

## 6. 기능 요구사항

| FR   | 요구사항                                                         | 강제 지점                     |
| ---- | ---------------------------------------------------------------- | ----------------------------- |
| FR-1 | 시계열은 1점 이상, horizon 은 1~365                              | `ForecastRequest` pydantic    |

## 12. 역산에서 드러난 격차

### G-1. 예측 구간이 기간에 따라 넓어지지 않는다 ★

`_interval` 은 **하나의 잔차 표준편차**로 전 구간에 같은 폭(±1.96σ)을 적용한다. 그래서 1일 뒤와 14일 뒤의
불확실성이 **동일하게** 표시된다. 실제 시계열 예측에서 구간은 기간이 늘수록 넓어져야 하며, 이 표현은
장기 구간의 신뢰도를 체계적으로 과대평가한다. 자금계획 근거로 쓰면 위험한 형태다.

### G-2. NaN 을 0.0 으로 치환해 실패가 성공처럼 보인다 ★

`_sanitize` 는 JSON 유효성을 위해 NaN/Inf 를 0.0 으로 바꾼다(BR-5). 그런데 `mape` 는 실측이 전부 0일 때
**의도적으로 NaN 을 반환**하고, 이 값이 응답에서는 `mape: 0.0` 이 된다 — 지표상 **완벽한 예측**으로 읽힌다.
예측값 자체도 마찬가지로 NaN → 0.0 이 되어 "0원 예측"과 "계산 실패"를 구분할 수 없다.

### G-3. 표본 밖 검증이 구현돼 있는데 노출되지 않는다

`service.backtest_split` 은 마지막 `test_size` 개를 홀드아웃해 **표본 밖** MAPE/RMSE 를 계산한다. 그런데
어떤 엔드포인트도 이 함수를 호출하지 않는다. API 가 내보내는 지표는 전부 **표본 내**라서 과적합을 감지할 수
없다 — 정작 그걸 감지할 코드는 이미 있는데 사문화돼 있다.

### G-4. 날짜 간격을 마지막 두 점으로만 추론한다

`_infer_step` 은 `dates[-1] - dates[-2]` 하나만 본다. 시계열 대부분이 일간인데 마지막 두 점만 3일 떨어져
있으면 **미래 날짜 전부가 3일 간격**으로 생성된다. 결측·불규칙 구간이 있는 실데이터에서 조용히 틀린 날짜를
만든다. (간격이 0 이하일 때만 1일로 폴백한다.)

### G-5. 데이터 소스가 없다

`settlement-service` 의 실 정산액을 끌어오는 경로가 없다(N1 은 이를 비목표로 선언). 현재 예측 대상은 요청
본문이거나, `demo_data.py` 가 만드는 **합성 시계열**(기저 10만 + 일 1,500 성장 + 주말 -2.5만/-4만 + 잡음)이다.
데모의 그럴듯한 정확도는 "모델이 자기가 만든 패턴을 맞춘 것"에 가깝다.

### G-6. 계절 폴백이 조용하다

계절 주기를 명시했는데 표본이 모자라면 **추세 전용 Holt-Winters** 로 내려간다. 응답 `model` 라벨이
`holt_winters_trend` 로 바뀌므로 정보는 있지만(BR-3), "왜 계절이 빠졌는지"는 로그에도 남지 않는다
(`n<4` 폴백과 적합 실패는 로그를 남긴다).

### G-7. 호출자·배선이 없고 인증도 없다

compose 정의, 게이트웨이 라우트, 호출하는 Java 서비스·프론트 코드가 모두 없다. 세 엔드포인트 모두 인증이
없다. CEO 대시보드가 이 서비스를 쓰는 배선은 존재하지 않는다.

### G-8. 관측 수단이 로그뿐이다

`/metrics` 도 카운터도 없다. 요청량·모델 선택 분포·폴백 발생률을 지표로 볼 수 없다.
