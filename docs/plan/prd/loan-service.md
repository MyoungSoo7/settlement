## 1. 배경과 문제

플랫폼에는 돈이 필요한 세 부류가 있다. **셀러**는 정산일까지 묶인 판매대금 때문에 재고를 못 늘리고,
**법인**은 설비·차량을 사려면 목돈이 필요하며, **개인**은 담보가 있어도 그것을 현금화할 창구가 없다.
은행에 가면 되지만, 플랫폼은 이들에 대해 은행이 갖지 못한 정보를 갖고 있다 — 정산 예정금, 매출 이력, 뉴스 평판.

| 문제               | 구체적 손상                                                                  |
| ------------------ | ---------------------------------------------------------------------------- |
| **셀러 자금 회전** | 판매는 됐는데 정산일까지 현금이 없어 매입·광고를 못 한다                     |
| **여신 판단 근거** | 재무제표만 보면 정성 리스크(평판·소송·리콜)를 놓치고, 평판만 보면 숫자를 놓친다 |
| **회수 불능**      | 담보 없이 나간 돈은 연체 후 회수 수단이 없고, 담보가 있어도 가치가 흔들린다  |

loan-service 는 **플랫폼이 이미 아는 정보(정산 예정금·재무·평판)를 결정적 정책 함수로 환산해** 한도와 요율을
정하고, 실행부터 상환·연체·담보 집행까지를 자체 원장과 함께 관리한다.

## 2. 목표 / 비목표

### 2.1 목표

- **G1 — 4개 여신 상품 한 서비스**: 선정산·기업신용·담보/개인신용·물건금융(리스·할부)을 공통 원장 위에서 운용한다.
- **G2 — 심사의 결정성**: 한도·등급·수수료는 전부 순수 함수(구간 매핑)이며 같은 입력에 항상 같은 답을 낸다.
- **G3 — 상환 자동화**: 선정산 대출은 정산 확정 이벤트로 자동 차감되고, 그 결과를 정산에 되돌려 준다.
- **G4 — 자체 복식부기**: 실행·수수료·상환·상각·담보 처분을 자기 원장에 전표로 남긴다.
- **G5 — 담보 관리**: 담보 재평가로 담보비율을 감시하고 마진콜·강제집행 단계를 밟는다.
- **G6 — 이중지급 차단**: 실행은 비관적 락 아래에서만 일어난다.

### 2.2 비목표 (명시적 경계)

- **실제 송금을 하지 않는다.** 자금 이체(펌뱅킹·FEP 전문)는 settlement payout 의 책임이다.
- **정산 원장을 소유하지 않는다.** 셀러 정산 예정금은 `seller_settlement_view` 프로젝션으로 읽고,
  차감 결과는 이벤트로 통지할 뿐 정산 금액을 직접 고치지 않는다.
- **신용평가사·등기부를 직접 조회하지 않는다.** 재무·평판은 각각 financial-statements/company 서비스 산출물이고,
  담보 가치는 입력값이다.
- **원리금 회계의 정답지가 아니다.** 전사 GL 집계는 account-service 몫이며 loan 은 자기 도메인 원장만 갖는다.

## 5. 핵심 유스케이스

### UC-1. 선정산 대출 → 자동 상환 saga

```
order/settlement 이벤트 ──► seller_settlement_view 프로젝션 적재(PENDING/CONFIRMED)
셀러: POST /loans          한도 = 미지급 정산예정금 × LTV × 평판 haircut
운영자: POST /{id}/disburse  (비관적 락 → 전표 → 이벤트, 한 트랜잭션)
settlement.confirmed ──► ApplyRepaymentService
   · 셀러 미상환 대출을 FIFO(오래된 순)로 락 조회 후 순차 차감
   · 차감 총액을 lemuel.loan.repayment_applied 로 발행
   · settlement 가 (정산액 − 차감액)으로 payout
```

**차감이 0이어도 발행한다** — settlement 가 전액 지급하도록 통지해야 멱등·정합이 성립한다.
이 발행을 생략하는 "최적화"는 정산 지급을 멈추게 한다.

### UC-2. 기업 신용대출 심사

```
GET /loans/corporate/credit/{stockCode}
  신용점수 = 안정성 40(부채비율) + 수익성 40(영업이익률·ROA) + 평판 20(뉴스 등급)
  등급 A≥80 B≥65 C≥50 D≥35 E<35,  E 는 대출 불가
  한도 = 자본총계 × equityLimitRatio(0.10) × gradeFactor(A1.0 B0.8 C0.6 D0.3 E0)
  수수료 = 원금 × dailyRate × termDays × gradeSurcharge(A1.0 B1.1 C1.25 D1.5)
```

실행은 전표 **2건**(대출채권/현금 + 미수수익/수수료수익, 수수료>0 일 때만)이 한 트랜잭션에 묶인다.

### UC-3. 담보대출과 담보 감시

담보 종류별 LTV 로 한도를 산출하고(주택담보는 유효담보가치 × LTV), 실행 후에는 재평가로 담보비율을 갱신한다.
담보비율이 **1.40 미만이면 마진콜**, **1.20 미만이면 강제집행** 단계로 넘어간다. 중도상환은 3년(1095일) 경과 시
수수료가 면제되고 그 전에는 1.2% 를 문다.

### UC-4. 물건금융(리스·할부)

취득가·선납금·보증금·잔존가치와 기간·이율로 월 납입 스케줄을 만들고, `APPLIED → APPROVED → ACTIVE` 로 개시한다.
개시 시 `LEASE_RECEIVABLE` 전표와 `lemuel.loan.lease_activated` 이벤트가 나간다. 이후 납입·연체·기한이익상실·
만기·중도해지를 상태로 관리하며, 중도해지는 별도 정산 견적(`EarlyTerminationQuote`)을 낸다.

## 7. 도메인 규칙 (BR)

### 7.1 상태머신

```
LoanAdvance   : REQUESTED → APPROVED → DISBURSED → REPAID  (↘ REJECTED, OVERDUE → WRITTEN_OFF)
CorporateLoan : REQUESTED → APPROVED → DISBURSED → REPAID  (↘ REJECTED)
SecuredLoan   : REQUESTED → APPROVED → DISBURSED → REPAID  (↘ REJECTED, DISBURSED → OVERDUE → DEFAULTED → WRITTEN_OFF)
Lease         : APPLIED → APPROVED → ACTIVE → {OVERDUE → DEFAULTED, MATURED, EARLY_TERMINATED}  (↘ REJECTED, CANCELLED)
Collateral    : PLEDGED → ACTIVE → RELEASED          MarginCall: OPEN → RESOLVED | ESCALATED
```

- **BR-1**: 상태는 전이 메서드로만 바꾼다. setter 직접 변경 금지.
- **BR-2**: 심사 계산(점수·한도·수수료)은 정책 클래스 밖에서 인라인으로 하지 않는다 — 경계값 테스트를 우회하기 때문이다.
- **BR-3**: 평판 부재는 **막지 않는다**(선정산 haircut 1.0, 기업 10점 중립). 데이터가 없다는 사실이 신용 판단이 되면 안 된다.
- **BR-4**: 실행은 비관적 락 안에서만. 락 없는 disburse 는 이중지급이다.

## 10. 역산에서 드러난 격차

### A. 문서·스킬이 여신 4종 중 2종만 다룬다 (규칙 정본 드리프트) — ✅ 2026-08-13 해소 (L-1)

> **조치**: `loan-domain-rules` 스킬에 담보/개인신용·물건금융 규칙을 추가했다 — 담보 유형별 LTV 표,
> CB 등급 밴드와 **미상 차단**(선정산 fail-open 과 반대인 이유 포함), 등급별 정액한도·가산금리,
> 보증료 1.2%/85%, 담보유지비율 1.40/1.20 판정과 실행 2경로, 중도상환 taper(1.2%·1095일),
> 리스 스케줄 산식(연금현가식·잔존가치 불변식)과 상태머신, 원장 계정 10종, 계약 토픽 7종,
> 안티패턴 6종 추가. `../../../SPEC.md` §3.3 에는 제목·물건금융 행·담보 운영 행을 넣고,
> "기존 6계정만 쓴다"는 낡은 서술을 계정 10종 현행으로 정정했다.
>
> 아래는 해소 전 상태 기록이다.

`loan-domain-rules` 스킬은 CLAUDE.md 가 **"서비스별 강제 도메인 규칙" 정본**으로 지정한 문서인데,
선정산·기업신용 2종만 기술한다. **담보/개인신용(SecuredLoan)과 물건금융(리스·할부)은 한 줄도 없다** —
담보비율 1.40/1.20 임계, 보증료 1.2%/85%, 중도상환 1095일 면제, 리스 상태머신 9종 같은 규칙이
스킬에는 존재하지 않는다. 에이전트가 이 스킬만 읽고 담보·리스 코드를 고치면 규칙을 모른 채 고친다.

`../../../SPEC.md` §3.3 도 제목은 "선정산 + 기업대출 + 담보/개인신용"까지만이고 **리스·할부는 없다**
(문서 전체에서 "리스"·"할부" 검색 결과 0건 — 2026-08-13 착지분 미반영).

### B. 여신 4종이 한 패키지에 평평하게 쌓여 있다

`loan/domain` 한 곳에 41개 클래스가 상품 구분 없이 놓여 있다(선정산·기업·담보·리스가 섞임).
서비스도 21개가 `application/service` 평면에 있다. 컴파일·테스트는 통과하지만, 상품이 하나 더 늘면
"이 클래스가 어느 상품 것인가"를 이름으로만 구분해야 한다. settlement 가 12개 서브도메인으로 나눈 것과 대비된다.

### C. 담보 재평가·강제집행에 **진입점이 아예 없다** — ✅ 2026-08-13 해소 (L-2)

> **조치**: `CollateralController`(`/loans/secured/{loanId}/collateral`)로 재평가·처분·대위변제 3개
> 진입점을 붙였다. 배치가 아니라 REST 인 이유는 재평가 값을 시스템이 스스로 알 수 없기 때문이다 —
> 부동산 감정가·금융자산 시세는 외부에서 들어오므로 "값을 들고 오는 쪽"이 부르는 API 가 먼저이고,
> 자동 수집(시세 이벤트 구독)은 그 위에 얹으면 된다. 인가는 운영자 전용, 처분·대위변제는
> `Idempotency-Key` 선점(`SecuredLoanController` 와 동형).
>
> **재발 방지가 본체다**: `LoanArchitectureTest#모든_인바운드_포트는_어댑터에서_호출된다` 를 신설해
> "구현했지만 도달 불가" 유형을 구조로 막는다. 도입 시점에 위반 2건(이 담보 유스케이스 둘)을
> 실제로 잡아냈고, 배선 후 0 이 됐다. 단위 테스트는 "호출하는 사람이 없다"를 볼 수 없다.
>
> 아래는 해소 전 상태 기록이다.

연체 스캔(`LoanOverdueScheduler`, 03:00)은 있으나 담보 쪽에는 배치가 없다. 더 정확히는 —
`RevalueCollateralService`·`EnforceCollateralService` 와 그 유스케이스 인터페이스는 구현되어 있고
단위 테스트도 있지만, **어떤 어댑터도 이들을 호출하지 않는다**. 컨트롤러·스케줄러·컨슈머 어디에서도
주입되지 않으며, 유스케이스 인터페이스를 참조하는 곳은 자기 구현체 한 곳뿐이다(전체 검색으로 확인).

즉 담보 재평가와 강제집행은 **코드로는 존재하고 런타임으로는 도달 불가능**하다. 마진콜(1.40)·
강제집행(1.20) 임계는 정책 상수로 박혀 있지만 그 판정을 트리거할 방법이 시스템에 없다 —
담보 가치가 반토막 나도 아무 일도 일어나지 않는다. 단위 테스트가 초록불이라 이 사실이 가려져 있다.

### D. 대출 상환차감이 실제 지급액에 반영되지 않는다 (돈이 새는 결함) — ✅ 2026-08-13 해소 (L-3)

> **조치(A안)**: 지급 생성을 확정 배치에서 **상환차감 수신 시점**(`ApplyLoanDeductionService`)으로 옮겼다.
> loan 이 차감 0 에도 항상 발행하므로 모든 정산에 트리거가 온다. 채권상계도 함께 옮겼다 — 확정 시점에
> 상계하면 대출로 갈 재원을 미리 소진한다. 확정 배치에서는 `RequestPayoutUseCase` 의존 자체를 제거해
> 지급을 만들 수 없게 했고, 오용 소지가 있던 `netPayoutFor()` 는 삭제했다.
> 검증: 단위 8건 + `PayoutWiringIntegrationIT` 5건(실 DB 로 차감이 송금액에서 빠지는지) · 모듈 1396건 GREEN.
> **후속**: loan 이벤트 유실 시 지급이 생성되지 않는다. 감지는 INV-6 의 payout 없는 정산 목록이며
> 현재 정보성이라, 시간 기반 경보로 격상하는 것이 남았다.

아래는 해소 전 상태 기록이다.

우선순위 문서화 문제로 적었다가 코드를 따라가 보니 **문서화가 아니라 미배선**이었다.

```
03:00 확정 배치  payout 금액 = immediate − 원천징수 − 채권상계   ← 여기서 확정(loan 차감 없음)
                 같은 트랜잭션에서 settlement.confirmed 발행
   ↓ (비동기)
loan            FIFO 로 대출 잔액 차감 + loan_repayments 기록 → repayment_applied 발행
   ↓
settlement      settlement_loan_deductions 에 기록  ← 기록만 하고 끝
04:00 지급 배치  저장된 payout.amount 를 그대로 송금
```

- `ApplyLoanDeductionUseCase.netPayoutFor()`(= `netAmount − deducted`)는 **호출자가 없다.**
- `Payout.amount` 는 `final` 이라 사후 감액도 불가하다(설계상 의도된 불변).
- 결과: **loan 은 대출 잔액을 줄이고 상환을 기록하는데, 셀러에게는 전액이 나간다.** 채권만 사라진다.
- 문서·주석은 반대로 적고 있다 — `loan-domain-rules` 는 "settlement 가 순지급액(amount − deducted)으로
  payout", `LoanRepaymentAppliedConsumer` javadoc 은 "차감액을 보존해 payout 시 순지급액으로 지급되게 한다".
  의도는 기록돼 있고 배선만 없다.

**차감 우선순위(L-3 정의)** — 기준은 "못 뗐을 때 이월되는가" 하나다:
**① 원천징수**(소실=과소징수) → **② 대출 상환차감**(loan 이 이미 상환 처리 → 못 떼면 손실) →
**③ 채권상계**(OPEN 채권으로 이월). 정본은 `settlement-domain-rules` 의 "지급액 차감 순서" 절.

**수정안 3종** (미결정 — 돈 경로라 설계 승인 후 착수):
- **(A) 지급 생성을 `repayment_applied` 수신 시점으로 미룬다** — loan 이 차감 0 이어도 항상 발행하므로
  모든 정산에 트리거가 온다(스킬이 명문화한 규칙). 가장 정합적이나, loan 이벤트가 유실되면 지급이 멈춘다
  (DLQ·재처리 경로 필수).
- (B) 지급 실행 시점에 기록된 차감으로 감액 — `Payout.amount` 불변이라 조정 레코드나 재생성이 필요하다.
- (C) 확정 시점에 loan 내부 API 동기 조회 — MSA 결합이 늘고 loan 장애가 정산 확정을 막는다.
