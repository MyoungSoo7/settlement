# RAG 지식베이스 적재 운영

AI 챗봇(ai-service)이 답변 근거로 쓰는 지식베이스를 리포에서 관리하는 방법. 설계 배경은
[ADR 0034](adr/0034-ai-service-rag-pgvector.md), 적재 대상 문서는 `docs/knowledge/` 에 있다.

## 원칙 — 등재된 문서만 적재한다

`manifest.txt` 에 경로가 적힌 파일만 적재된다. 디렉터리에 파일을 두는 것만으로는
적재되지 않는다.

기본값이 "적재"가 아니라 "제외"인 이유: 적재된 문서는 이후 **모든 사용자 답변의 근거**로 프롬프트에
실린다. 기본값이 "적재"라면 언젠가 누군가 내부 런북이나 설계 문서를 이 디렉터리에 떨어뜨리고, 그
내용이 사용자에게 흘러나가기 시작한다. 그 사고는 조용히 일어나고, 이미 나간 답변은 되돌릴 수 없다.

## 문서를 추가하는 절차

1. `docs/knowledge/<이름>.md` 로 작성한다. 첫 줄은 `# 제목` (H1) — 제목은 여기서 파생된다.
2. `manifest.txt` 에 파일명을 한 줄 추가한다.
3. `golden-questions.txt` 에 그 문서를 찾아야 할 질문을 1~2개 추가한다.
4. `python3 scripts/knowledge/sync_knowledge.py --check-manifest` 로 정합성을 확인한다.

제목과 출처 URI 는 매니페스트에 적지 않는다 — H1 과 파일명에서 파생된다
(`guide-funds.md` → `kb://guide-funds`). 적을 게 없으면 어긋날 수도 없다. 매니페스트에 제목을 따로
적으면 문서를 고칠 때 한쪽만 바뀌고, 그 상태로도 동기화는 조용히 성공한다.

## 무엇을 넣고 무엇을 넣지 않는가

**넣는다** — 셀러·CEO 에게 그대로 읽혀도 되는 이용 안내, 정책·요율 설명, 절차 안내.

**넣지 않는다** — 내부 설계·아키텍처, 런북, ADR, 미구현 기능 목록, 설정키·클래스명·API 경로,
보안 규칙과 그 우회 방지책(챗봇 자신의 방어 설계도다), 미해결 리스크 서술.

### 문서를 쓸 때

- **문단 하나가 단독으로 읽혀야 한다.** 검색은 문서 전체가 아니라 문단 하나를 뽑아 근거로 올린다.
  "위에서 설명한 것처럼" 같은 앞뒤 참조를 쓰면 그 문단만 뽑혔을 때 뜻이 무너진다. 대명사 대신
  주어를 반복한다 — "그것은" 이 아니라 "선정산 대출은".
- **한 문단 1200자 이하.** 청크 상한(`app.ai.rag.chunk-max-chars`)이다. 넘으면 문단 중간에서 잘린다.
- **수치에는 근거를 붙인다.** 법령·감독기관 수치는 1차 출처 링크를, 내부 정책값은 "기본 설정값이며
  운영 환경에 따라 다를 수 있다"는 단서를 문서 안에 남긴다. 챗봇은 문서에 적힌 대로 말한다.

## 동기화

```bash
# CI 와 같은 검사 — 네트워크 없이 매니페스트/파일 정합성만
python3 scripts/knowledge/sync_knowledge.py --check-manifest

# 무엇이 바뀔지만 확인 (쓰지 않음)
export KNOWLEDGE_ADMIN_TOKEN=<ADMIN JWT>
python3 scripts/knowledge/sync_knowledge.py --base-url http://localhost:8080 --dry-run

# 실제 동기화 — 고아 문서 회수 + 검색 검증까지
python3 scripts/knowledge/sync_knowledge.py --base-url http://localhost:8080 --prune --verify
```

토큰 대신 `--email/--password` 로 로그인해도 된다. `/auth/login` 은 IP 당 분당 5회 제한이 있다.

- `--prune` 은 매니페스트에 없는데 적재돼 있는 문서를 지운다. 없으면 경고만 하고 넘어간다 —
  삭제는 명시적 의사표시가 있을 때만 한다.
- `--verify` 는 골든 질문을 실제로 검색한다. **이 단계를 건너뛰지 말 것.** 적재 200 OK 는
  "벡터가 저장됐다"까지만 증명한다. 임베딩 모델·차원·유사도 임계값 중 하나만 어긋나면 적재는
  성공하고 검색만 조용히 빈손이 된다.

본문 변경 여부는 **서버가** 판정한다(`skipped: true` = 재임베딩 없음). 서버가 저장하는 해시는
PII 마스킹을 거친 본문의 해시라, 로컬에서 계산한 해시로 미리 거르면 판정이 틀린다.

## 켜기 전 확인

RAG 는 기본으로 꺼져 있다(`app.ai.rag.enabled=false`). 켜기 전에:

1. **대상 DB 에 pgvector 가 있고 앱 계정이 슈퍼유저인가.** 마이그레이션이 `CREATE EXTENSION vector`
   를 실행하고, 실패하면 부팅이 멈춘다. pgvector 는 trusted 확장이 아니라 슈퍼유저를 요구한다.
2. **`GEMINI_API_KEY` 가 설정됐는가.** 없으면 적재는 503, 검색은 근거 0건이다(챗봇 자체는 동작한다).
3. **`app.ai.embedding.dimension` 이 스키마의 `vector(768)` 과 같은가.** 다르면 적재 INSERT 가 깨진다.

지식베이스가 비어 있으면 켜도 답변은 달라지지 않는다 — 근거 0건이면 RAG 이전과 같은 경로를 탄다.
즉 **적재가 끝나기 전에 켜는 것은 아무 효과가 없고, 적재만 하고 켜지 않는 것도 마찬가지다.**

## CI

`harness-guard` 워크플로가 매 PR 에서 `--check-manifest` 를 돌린다. 잡는 것은
**문서를 추가하고 매니페스트 등재를 잊은 경우**다. 그대로 두면 그 문서는 적재되지 않은 채
"썼으니 챗봇이 안다"고 오해하게 된다.
